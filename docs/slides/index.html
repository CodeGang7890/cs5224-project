Architecture · Google Cloud, Singapore

A SaaS built on PaaS, in three planes

SaaSAnsera
PaaSCloud Run · Pub/Sub · Cloud SQL · Vertex AI
IaaSGoogle Cloud, asia-southeast1
  1. Control / client plane
  2. Message plane
  3. Payment plane
  4. Shared platform

So, Ansera is a SaaS built on PaaS, that is Cloud Run, Pub/Sub, Cloud SQL and Vertex AI, running on Google's IaaS in the Singapore region. And our architecture consists of three planes:

The control, or client, plane. This is where business owners set up their AI admin. They use the frontend on Firebase Hosting, and every API call enters an independent load balancer with Cloud Armor, while Cloud Run spreads requests over healthy instances. Behind it, configuration-service is the main backend. It manages the database and stores each business's configuration and information.

The message plane. Meta's WhatsApp calls the messaging-ingester, which only verifies and queues messages. The messaging-service runs the messages with Gemini. And each service scales out on its own, with dynamic horizontal scaling.

The payment plane shares the same shape as the message plane, but with the processing-service generating the invoice PDFs and emailing them to customers through Brevo, with Cloud Storage to store them.

And then, we also have the shared platform, including these services, all declared in Terraform.

User flow · the customer's point of view

① A customer messages the shop, through to a payment link

  1. Signed webhook in
  2. Signature verified, published
  3. Kept in the queue
  4. Cloud SQL → LLM reply
  5. Reply with the shop's token
  6. CONFIRM → invoice + link

Alright, on to the customer's point of view now. When a customer sends a message to the shop via WhatsApp, Meta will post a signed webhook through the load balancer to messaging-ingester.

configuration-service then verifies the signature, and the message is published to Pub/Sub.

Every message will be kept in the messaging queue, so a fast webhook never has to wait for a slow LLM turn.

The worker queries Cloud SQL, then talks to the LLM to generate a response.

The reply goes out through configuration-service, along with the business's own WhatsApp token.

After an order is finalized, on the CONFIRM message, the order is saved with its stock or booking on hold, processing-service sends out an invoice by email, and payment-ingester creates a Xendit payment link.

User flow · the customer's point of view

② Paid: receipt and reminders

  1. Pay on Xendit's page
  2. Verified, paid · receipt by email + WhatsApp
  3. Hourly reminders

The customer completes the payment fully on Xendit's hosted page, so no card data is recorded on Ansera.

processing-service proceeds to verify the payment amount, marks the order as paid, and generates the receipt, which is sent to the customer by email and WhatsApp.

In between all these payment mechanisms, Cloud Scheduler runs notification-job every hour. It queries Cloud SQL to process payment reminders for unpaid items, and booking reminders within 24 hours.

Event pipeline · a closer look at the queues

Answer Meta fast, handle each message once

⚡ 200 in ~100 ms

The ingester only checks the signature and publishes. If the publish fails: 503, and Meta retries

🪪 Claimed by its WhatsApp ID

Pub/Sub delivers at least once: each message is claimed by its unique ID, so it's processed once

🧵 A burst gets one reply

No ordering key, on purpose: each new message bumps the chat's version, and a turn saves its reply only if the version is unchanged, so one reply answers them all

Now we take a closer look at the queues. An LLM turn can take several seconds. So messaging-ingester only checks the message signature, publishes the message to Pub/Sub, and responds with success, 200, in about 100 milliseconds. If publishing fails, it answers error 503, and Meta will retry. watch the message

We make sure each message is processed exactly once. Each message is claimed by its unique WhatsApp ID, so a redelivery is skipped.

Messages can come in successive bursts within a short period. By utilizing the chat version and optimistic locking, an LLM turn will only answer the latest message in a single chat.

Event pipeline · a closer look at the queues

Failures are expected, so we designed for them

🔢 One turn, one transaction

State, order and reply commit together, in one transaction, under a row lock

☠️ Retry, then dead-letter

Poison messages back off from 30 s to 10 min; after 5 failed attempts, the dead-letter queue

💳 Payments too

Only a pending order can change, so a repeated Xendit event is a no-op, and a late expiry never cancels a paid order

One turn commits its state, order and reply in one transaction, under a row lock. watch the turn

Poison messages are retried with delays between 30 seconds and 10 minutes, and after 5 failed attempts they go to a dead-letter queue.

The same system applies to payment-ingester: each Xendit event is stored once, and a late expiry never cancels a paid order.

Behind the scenes, the LLM tries to understand the customer's query and makes a response for it.

    
A router call returns the intents as JSON, preserving their order: order, booking, question, or order status.

    
Orders and bookings run a state machine. The LLM extracts the details, and the system checks them against real-time stock and free slots.

For security, our entire backend is encapsulated within a Virtual Private Cloud, and isolated from the open Internet. Public traffic is only allowed through an HTTPS load balancer, which exposes a single IP address and domain for our backend, and routes requests to configuration-service, payment-ingester and messaging-ingester. The remaining containers and Cloud SQL are not exposed. a direct hit bounces

    
Each container is also provisioned with its own service account, following the principle of least privilege, and is assigned minimum permissions.

    
Sensitive data, such as API keys and account credentials, is stored in Secret Manager, and only exposed to containers as environment variables.

    
Cloud Armor is GCP's network security service and web application firewall. It protects load balancers and containers from DDoS attacks and OWASP Top 10 vulnerabilities, such as cross-site scripting and SQL injection. We have implemented it on our public-facing load balancer, with the appropriate rulesets. attacks bounce

To enable scalability within our SaaS application, all tenants' data and application logic are handled by the same PostgreSQL database and backend containers. To enable multi-tenancy for multiple businesses, we use the following application-level logic to implement user isolation.

    
First, our application uses APIs that implement authentication, for example JSON Web Tokens, or JWTs, to authenticate incoming webhook traffic, and categorise it into each business's operation.

    
We also implement business-ID based tenant isolation, which assigns a unique business ID to each registered business, to limit object reads and writes to only its own chats, orders and catalog items. Each WhatsApp number must only be used for one business: no duplicates are allowed across businesses. other rows fade, 403

    
Additional unique constraints are also applied for each business, such as no duplicate product names, to ensure there's no ambiguity among product offerings and subsequent orders.

Our PostgreSQL database also implements column indexing on order status, chat session IDs and business IDs, to speed up row lookups, along with prioritising strong consistency over availability, to prevent serving stale data, such as accurate stock counts and payment values.

    
To handle concurrency, we implement pessimistic locking on payments and stock transactions, to avoid race conditions, while optimistic locking is used for customer chats, which rely on asynchronous LLM calls and incrementing chat versions.

    
SQL injection attacks are also mitigated by using well-defined ORMs with sanitized serializers, along with Cloud Armor policies on the external load balancer.

    
Objects related to a business, such as receipts and invoices, are stored in a shared Cloud Storage bucket, grouped by tenant ID. Individual customers don't have bucket access; instead, they get 7-day signed URLs to open and download their files. Object lifecycle management policies automatically move older files to Archive storage, to optimise storage costs.

Limitations

  
What it can't do yet, and how we'd fix it

  

    
💬
Text only, one number

      
  • Text messages only, through WhatsApp
  • One WhatsApp number per business

      
The fixMultimodal input, like images

    
📚
Very large catalogues

      
  • The whole catalogue has to fit in the model's input

      
The fixRAG: retrieve only the items a question needs

    
🌏
One region, one cloud

      
  • Singapore only: recovering from a regional outage is manual
  • Depends on GCP: some vendor lock-in

      
The fixA backup deployment in Jakarta, with cross-region traffic routing and failover

  

  

    
Some of the limitations of the current version of Ansera are: the system only supports text messages through WhatsApp, and each business can only connect to one WhatsApp number.

    
To solve this, later we would add multimodal input, like images.

    
A very large catalogue may not fit into the model's input.

    
So, in a later version, we can use RAG.

    
The system currently runs in the Singapore region, so recovering from a regional outage would still require a manual process. We also depend on GCP, which creates some vendor lock-in.

    
To improve this, we would add a backup deployment in Jakarta, with cross-region traffic routing and failover.
