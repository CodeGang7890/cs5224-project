# GCP prototype infrastructure

Terraform targets an **existing, billing-enabled GCP project**. All files in this folder are infrastructure code; no app source files are changed. The default compute region is `us-central1`, which is one of the three US regions eligible for Cloud Storage Always Free usage. Resources still cost money once their free allowances are exceeded.

## What is provisioned

| Component                  | Terraform behavior                                                                                                                                                                                                                                                                                                                |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Artifact Registry          | One regional Docker repository, `apps`.                                                                                                                                                                                                                                                                                           |
| Cloud Storage              | Private Standard bucket in the compute region. The project ID based default name can be overridden.                                                                                                                                                                                                                               |
| Pub/Sub                    | Payment and messaging queues, plus the existing notification topic, each with a pull subscription.                                                                                                                                                                                                                                |
| Cloud Scheduler            | One hourly UTC job that invokes the notification Cloud Run Job through the Cloud Run Jobs API. It is paused until `enable_notification_scheduler = true`.                                                                                                                                                                         |
| Secret Manager             | Secret containers for Django, JWT, internal API access, LLM, WhatsApp, and Xendit. Terraform generates the Django, JWT, and internal API key versions. Add external API token versions separately.                                                                                                                                |
| Cloud Run                  | Five backend services are created with the hello placeholder image unless an image is set in `service_images`; Cloud Build replaces the image on matching pushes. US services keep one instance warm by default and can scale to three. Messaging-service and processing-service also keep CPU available for their pull consumers. |
| Cloud Run Jobs             | `notification-job` runs once and exits. It connects to Cloud SQL and is started hourly by Cloud Scheduler; its image is updated by a separate Cloud Build trigger.                                                                                                                                                                |
| Vertex AI demo             | Optional standalone `vertex-ai-demo` Cloud Run service with one warm instance, a dedicated runtime service account, and a Cloud Build image/deploy trigger. Disabled by default.                                                                                                                                                                      |
| Cloud Logging / Monitoring | A logs-based metric counts Cloud Run HTTP 4xx/5xx responses, with an alert policy for 10 or more across the services in a five-minute aligned interval. An email channel is created when `alert_notification_email` is set.                                                                                                       |
| Cloud SQL                  | Optional small PostgreSQL 17 instance, database, user, and password secret. **Billed while running.**                                                                                                                                                                                                                             |
| Cloud DNS                  | Optional public zone and records for a domain you own. **Billed even when idle.**                                                                                                                                                                                                                                                 |
| Cloud Build                | Backend build/deploy triggers and a Firebase Hosting frontend deployment trigger for a linked GitHub repository.                                                                                                                                                                                                                  |
| Vertex AI                  | Gemini API enabled by default; grants `roles/aiplatform.user` to the configuration-service runtime identity. Model and location are configurable.                                                                                                                                                                                 |
| Firebase                   | Optional Firebase enrollment, Ansera web app, and a Hosting site. Enrollment cannot be undone.                                                                                                                                                                                                                                    |

The architecture also shows an in-memory store, load balancer, and observability. Those were not in the requested service list and are not provisioned here. Cloud Run provides a service URL; the Cloud DNS zone does not automatically map a custom domain to Cloud Run. That mapping requires a later domain or load-balancer decision.

## Prerequisites and authentication (PowerShell)

1. Install [Terraform](https://developer.hashicorp.com/terraform/install) and the [Google Cloud CLI](https://cloud.google.com/sdk/docs/install).
2. Create/select a GCP project, enable billing, and ensure your identity can enable APIs and create the listed resources. The organization may also restrict public Cloud Run access.
3. Authenticate in your own browser. Do not put a service-account JSON key in this repository:

   ```powershell
   gcloud auth login
   gcloud config set project YOUR_GCP_PROJECT_ID
   gcloud auth application-default login
   gcloud auth application-default set-quota-project YOUR_GCP_PROJECT_ID
   ```

4. Copy `terraform.tfvars.example` to `terraform.tfvars` and set `project_id`. The latter is Git-ignored. Run from this directory:

   ```powershell
   terraform init
   terraform fmt -check
   terraform validate
   terraform plan -out=prototype.tfplan
   terraform apply prototype.tfplan
   ```

The default Terraform state is **local** (`terraform.tfstate`, Git-ignored). It contains generated secret values, so keep it private and back it up. For group collaboration, migrate to a private versioned GCS state bucket before multiple people apply changes; create the bucket separately, then add a `backend "gcs"` block with its bucket and prefix and run `terraform init -migrate-state`. The state bucket itself has storage and operation costs. Never send state files or credentials in chat or commit them.

## Deployment order

1. Apply the base resources, with `enable_firebase = true` when ready. This adds Firebase to the existing project (a one-way action), creates the Ansera web app, and creates a Hosting site. The site ID must be globally unique; change `firebase_hosting_site_id` if `cs5224-ansera` is unavailable.
2. Build `frontend-app` with `npm ci` and `npm run build`. The Firebase Hosting config in this folder serves `frontend-app/dist` and rewrites client-side routes to `index.html`.
3. In Cloud Build > Repositories > 2nd gen, create a GitHub connection and authorize/install the Cloud Build GitHub App for `CodeGang7890/cs5224-project`. Set `github_connection_name = "ansera"`. With `enable_ci_cd = true` and the selected service names in `ci_cd_services`, Terraform links the repository and creates one build/deploy trigger per selected backend service. The frontend trigger builds and deploys Hosting on pushes to `main` when Firebase is enabled.
4. The five Cloud Run services are created on the first Terraform apply with the hello placeholder image unless `service_images` contains an image reference. `ci_cd_services` is empty by default; select any of `configuration-service`, `messaging-service`, `processing-service`, `payment-ingester`, or `messaging-ingester` when its Dockerfile is ready to build and deploy. Push changes to a selected service folder on `main`; Cloud Build builds the Dockerfile, pushes an immutable commit-tagged image to Artifact Registry, and updates its Cloud Run service.
5. When `enable_cloud_sql = true`, Terraform creates the `notification-job` Cloud Run Job with the Cloud Run hello placeholder and configures its Cloud SQL socket and database credentials. Its Cloud Build trigger builds `notification-job/Dockerfile` and updates the job image on changes under `notification-job/`.
6. The scheduler remains paused by default. After the notification job image has been built and its database connection has been verified, set `enable_notification_scheduler = true` and apply. Cloud Scheduler then invokes the Cloud Run Jobs `:run` API hourly using a dedicated OAuth service account. The notification script currently logs draft reminders; it does not send WhatsApp messages yet.
7. To deploy the separate browser demo, set `enable_vertex_ai_demo = true` in `terraform.tfvars` and apply. The service uses its own Vertex AI runtime identity. If CI/CD is enabled, push a change under `vertex-ai-demo/` to build, push, and deploy the container. Keep `vertex_ai_demo_allow_unauthenticated = false` for IAM-protected access; set it to `true` only when the public demo is needed. Public requests can incur Gemini usage charges.
8. Cloud Run HTTP error alerting is configured for 10 or more 4xx/5xx request logs in a five-minute aligned interval, summed across services. Set `alert_notification_email` to a verified email destination to receive notifications; otherwise, Monitoring still opens incidents without sending an external notification. User-defined log-based metrics can incur monitoring charges.

In Singapore, Cloud Run services `configuration-service`, `payment-ingester`, `messaging-ingester`, and the Vertex AI demo receive public invoker access for browser, webhook, or demo traffic. The other services remain private. The old US Cloud Run endpoints are private, including the former Meta bridge. Set `django_allowed_hosts` when using a custom domain.

### Payment ingester deployment

The active `payment-ingester-sg-main` trigger builds changes under `payment-ingester/` on `main`, pushes `asia-southeast1-docker.pkg.dev/cs5224-ansera/apps/payment-ingester:<commit>` to Artifact Registry, and deploys the Singapore Cloud Run service. The image is built from the Dockerfile; Artifact Registry stores the image, not the Dockerfile. To deploy an existing commit immediately, run `gcloud builds triggers run payment-ingester-sg-main --region=asia-southeast1 --branch=main --project=cs5224-ansera`.

The payment service uses the Terraform-managed `payment-queue` topic and its dedicated publisher identity. Its Xendit API key comes from `xendit-api-key` and the webhook callback token from the existing `xendit-webhook-key` Secret Manager secret. Both need an enabled version before Cloud Run can start. Terraform generates `internal-api-key` and shares it with configuration-service, messaging-service, messaging-ingester, and payment-ingester; do not use the application's development default in production. The active Singapore messaging service uses the Singapore payment-ingester URL. The Xendit webhook destination is `https://payment-ingester-gq6jjn4afq-as.a.run.app/webhook`, with the existing callback token. The public Singapore payment service checks that token on `/webhook` and the internal key on `/payments`.

The payment topic has a **pull** subscription, `payment-queue-worker`. Terraform supplies processing-service with the matching project, topic, and subscription names and enables its consumer. Processing-service keeps one instance with CPU available to poll the subscription while idle.

## Logging in with Google / Facebook (Identity Platform)

Owners can log in (or sign up) with Google or Facebook as well as a username and password (`identity.tf`). frontend-app runs the popup with the Firebase JS SDK, and configuration-service turns the ID token into its usual JWTs (`FIREBASE_PROJECT_ID`). With `enable_firebase`, Terraform enables Identity Platform (this can't be undone), sets the authorized domains, gives configuration-service `FIREBASE_PROJECT_ID`, and builds the frontend with the Firebase web app's config. The login popup uses the Hosting site's domain (`<site>.web.app`) as its auth domain, so **deploy the frontend before trying it**, even locally. The providers aren't in Terraform (so their secrets stay out of its state): each needs an OAuth client made by hand, entered in the console.

1. **Redirect URI** for both providers: `terraform output identity_oauth_redirect_uri` (`https://cs5224-ansera.web.app/__/auth/handler`).
2. **Google:** Google Auth Platform → Branding / Audience: set up the consent screen (**External**, so any Google account can log in; while it's in testing, add testers). Clients → Create client → Web application: authorized JavaScript origins `https://cs5224-ansera.web.app` and `http://localhost:5173`; the redirect URI above.
3. **Facebook:** a Meta app with **Facebook Login** (a _Consumer_ app is simplest; our WhatsApp app is a Business app, whose login is Facebook Login for Business). Facebook Login → Settings → Valid OAuth redirect URIs: the redirect URI above. Its `email` and `public_profile` permissions need no App Review; going Live needs the privacy policy URL (`https://cs5224-ansera.web.app/privacy.html`).
4. **Identity Platform → Providers → Add a provider**: Google (its client ID and secret) and Facebook (its App ID and App Secret).
5. For local development, copy `terraform output firebase_web_config` into the repository's `.env` (`FIREBASE_API_KEY`, `FIREBASE_AUTH_DOMAIN`, `FIREBASE_PROJECT_ID`).

Terraform owns the **authorized domains** (localhost and the Hosting site): add others in `identity.tf`, not in the console, or the next apply removes them.

For local Terraform runs with user ADC, set its quota project with `gcloud auth application-default set-quota-project cs5224-ansera`. The Google providers also explicitly send this project for API quota and billing (`versions.tf`). If Identity Platform was already enabled in the project before Terraform managed it, import it once with `terraform import 'google_identity_platform_config.auth[0]' projects/cs5224-ansera/config` before applying; creating an existing config returns `INVALID_PROJECT_ID`.

## WhatsApp Embedded Signup ("Connect with Facebook")

Businesses connect WhatsApp only through our Meta app, and this is always on. Setup:

1. **Meta App Dashboard** (our app):
   - **Facebook Login for Business → Settings**: turn on Client OAuth login, Web OAuth login, Enforce HTTPS, Embedded Browser OAuth Login, Use Strict Mode for redirect URIs and Login with the JavaScript SDK. Add the frontend's domain (e.g. `cs5224-ansera.web.app`) to _Allowed domains for the JavaScript SDK_ and `https://cs5224-ansera.web.app/` to _Valid OAuth redirect URIs_.
   - **Facebook Login for Business → Configurations**: create one from the _WhatsApp Embedded Signup_ template and note its configuration ID.
2. **App Secret** (before the first apply; from a protected local file, not the command line): `gcloud secrets versions add meta-app-secret --data-file=…` (App settings → Basic → App secret). Terraform references this existing secret; its container is not Terraform-managed. Set `meta_app_secret_version` to the enabled version that belongs to the selected Meta app; configuration-service uses that specific version.
3. **`terraform.tfvars`**: set `meta_app_id`, `meta_embedded_signup_config_id`, `meta_app_secret_version`, and `meta_webhook_verify_token` to the values configured in the Meta App Dashboard. Keep `terraform.tfvars` ignored and private. Set `messaging_ingester_public_url` only if it isn't the Cloud Run default URL. Apply. configuration-service gets `META_APP_ID`, `META_APP_SECRET`, `META_APP_WEBHOOK_VERIFY_TOKEN` and `MESSAGING_INGESTER_PUBLIC_URL`, and the frontend build gets `VITE_META_APP_ID` / `VITE_META_CONFIG_ID`. Terraform writes the webhook token to a Secret Manager version; this value is also stored in private Terraform state. Without a configuration ID, the Connect with Facebook button does nothing.
4. **Our app's webhook** (App Dashboard → WhatsApp → Configuration): Callback URL from `terraform output meta_app_webhook_url`, Verify token from `terraform output -raw meta_webhook_verify_token`; subscribe to `messages` and `account_update`. Do this before any business connects: Meta refuses to redirect a business's webhooks until our app is subscribed to `messages` ("(#100) Before override the current callback uri, your app must be subscribed to receive messages"). Each business's messages are then redirected to its own `/webhook/<id>` automatically.

When changing to a different Meta app, configure the frontend domain and webhook in that app too. WhatsApp accounts connected through the previous app may need to reconnect because the backend now verifies its app webhooks with the new App Secret.

The app works for Facebook accounts with a role on it while it's in development mode. Onboarding outside businesses needs Meta business verification, App Review and Tech Provider status.

### Persistent backend settings

Processing-service keeps invoice email enabled with the Ansera sender and Brevo SMTP relay. `SMTP_PASSWORD` reads the existing `smtp-password` Secret Manager secret; Terraform grants its runtime account access. Keep the sender verified with Brevo.

Terraform defines the Cloud Run environment for configuration-service, messaging-service, and processing-service in `run.tf`. Configuration-service has the public messaging-ingester URL and Meta Graph API URL. Messaging-service has its Firebase CORS origins, configuration-service API URL, and messaging Pub/Sub subscription. Processing-service has its configuration-service URL, payment Pub/Sub subscription, Cloud SQL socket and database settings, invoice bucket, and currency. Both Pub/Sub consumers are enabled and keep one Cloud Run instance with CPU allocated outside requests. These two instances incur continuous charges, even without HTTP traffic.

`CONFIGURATION_ENCRYPTION_KEY` on configuration-service references the existing `configuration-encryption-key` Secret Manager secret, with a dedicated runtime access grant. Five existing WhatsApp configuration rows were re-encrypted from the old `django-secret-key` fallback before this reference changed. Keep both secret versions available for rollback; to rotate this encryption key again, migrate saved credentials before switching the Cloud Run reference. `DJANGO_SECRET_KEY` continues to use `django-secret-key` independently. Processing-service references the existing `internal-api-key` and `cloud-sql-db-password` secrets; Terraform grants its runtime service account access to those secrets, the invoice bucket, and signing invoices' download URLs. No secret value is stored in Cloud Run environment configuration as plain text. Generated secret values already exist in the private Terraform state, so protect and back up that state.

The one-time [migration helper](migrate_configuration_encryption_key.py) uses Cloud SQL Python Connector (`pg8000`) and Secret Manager through Application Default Credentials. Run `check` before switching keys, `forward` immediately before deploying the new Cloud Run revision, and `verify` after it is ready. `reverse` re-encrypts records for the old key if you also roll back the Cloud Run revision. The helper prints counts only. Avoid writes to WhatsApp configuration during a key cutover.

Terraform configures CORS on `configuration-service` for local Vite development and, when Firebase is enabled, both Hosting domains. Add custom frontend origins with `additional_browser_origins` and apply Terraform; changing the frontend build alone does not update backend CORS. The browser sends Chat Sandbox messages to `configuration-service`, which authenticates the user and forwards them to private `messaging-service`. Terraform gives the configuration runtime account Cloud Run Invoker permission, sets `MESSAGING_SERVICE_URL` and `MESSAGING_SERVICE_REQUIRE_ID_TOKEN`, and provides both services the same JWT signing secret. Applying the new JWT secret invalidates existing logins; users must sign in again. Set `messaging_service_url` if the private service's URL differs from this project's default. Messaging-service also receives the Cloud SQL socket and app database credentials when Cloud SQL is enabled.

## Firebase, DNS, and queues

- `enable_firebase = true` adds Firebase to the existing project and creates the `Ansera` web app plus a Hosting site. The site URL is available as the `firebase_hosting_url` Terraform output. It also turns on Identity Platform, for logging in with Google / Facebook (below).
- The Firebase Hosting trigger uses `infrastructure/firebase.json` and `infrastructure/cloudbuild-frontend.yaml`. It builds the Vite SPA and deploys it with Firebase CLI using the Cloud Build service account's Application Default Credentials. The build service account receives Firebase Hosting Admin when both Firebase and CI/CD are enabled.
- Set `dns_domain` to a domain you control to create a public zone. Point your registrar at `dns_nameservers`; add desired `dns_records` after the target IP/hostname is known. This zone alone does not create a load balancer or Cloud Run custom domain.
- The payment and messaging Pub/Sub subscriptions are **pull** subscriptions. Messaging-service and processing-service keep CPU allocated outside requests so they can poll while idle. All Cloud Run services have a service-level minimum of one instance; this incurs ongoing instance charges. The notification Cloud Run Job is invoked directly by Cloud Scheduler, not from the notification Pub/Sub subscription.
- Secret containers for third-party tokens intentionally have no versions. Add values with `gcloud secrets versions add SECRET_ID --data-file=FILE` using a protected local file, then configure the relevant app and runtime IAM. Avoid passing secrets in command arguments or Terraform variables.

## Vertex AI / Gemini integration

Terraform enables `aiplatform.googleapis.com` and grants `roles/aiplatform.user` to the services in `vertex_ai_services`. The active Singapore `messaging-service` owns the chat workflow. Its runtime settings select `LLM_PROVIDER=vertex_ai`, `LLM_MODEL=gemini-3.5-flash-lite`, and `GOOGLE_CLOUD_LOCATION=global`. Cloud Run and the active object bucket are in `asia-southeast1`; Gemini 3.5 Flash-Lite Standard PayGo uses the global endpoint, which does not guarantee processing in Singapore. See Google's [model locations](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-5-flash-lite) and [429 guidance](https://cloud.google.com/vertex-ai/generative-ai/docs/error-code-429).

`messaging-service/app/llm_vertex.py` uses the Google Gen AI SDK with its Cloud Run service account. It provides structured extraction, reply generation, and read-only tool calls for the existing chat flow. A sandbox turn can make multiple sequential model requests, so its response time can exceed that of a single short prompt. The app currently converts a Vertex 429 to an HTTP 503. If capacity errors recur, add bounded exponential-backoff retries to that adapter. For local development, use `gcloud auth application-default login`; do not copy credentials into an image or commit them.

See Google's [Gen AI SDK for Vertex AI](https://cloud.google.com/vertex-ai/generative-ai/docs/sdks/overview), [Gemini API pricing](https://cloud.google.com/vertex-ai/generative-ai/pricing), and [model list](https://cloud.google.com/vertex-ai/generative-ai/docs/learn/models).

## Cost notes

Google's free quotas are shared at the billing-account level where stated and may change. Cloud Storage Always Free covers Standard storage in `us-west1`, `us-central1`, and `us-east1`; it does **not** mean unlimited free storage, requests, or transfer. Cloud Scheduler has three free jobs per billing account. Cloud Run, Pub/Sub, Cloud Build, Artifact Registry, and Secret Manager each have distinct limits. Cloud SQL's ordinary small instance is billed continuously; a separate, time-limited Cloud SQL trial may be available for a new project but is not the same as this Terraform instance. Cloud DNS charges for managed zones and queries. External APIs and network egress can also cost money. Set a GCP Billing budget and alerts before applying; a budget alert does not automatically stop spend.

Current vendor pages: [Google Cloud Free Tier](https://cloud.google.com/free), [Cloud Storage pricing](https://cloud.google.com/storage/pricing), [Cloud Scheduler pricing](https://cloud.google.com/scheduler/pricing), [Cloud SQL trial](https://docs.cloud.google.com/sql/docs/postgres/free-trial-instance), [Cloud DNS pricing](https://cloud.google.com/dns/pricing).
