# CLAUDE.md: messaging-service

Guidance for Claude Code when working in `messaging-service/`.

## What this is

A **FastAPI** backend for Ansera Business Admin, on port **8004** (it moved from 8001, which is reserved for payment-ingester). It provides:
- `GET /`: hello world / health check.
- `POST /chat`: a **one-off** chat with a local LLM through **Ollama**. Single prompt in, single reply out, no history.
- A **Pub/Sub pull consumer** (the user asked) of the customer messages `../messaging-ingester` publishes (`whatsapp-inbound-messages`), and `GET /consumer` (its status). **Each message is answered by the chat flow** (`app/inbound.py` `handle_inbound`): a known business; a message that isn't text (photo, document, voice, …; the user asked: not left silent) skips the chat flow: `answer_unsupported` saves a placeholder (`[Photo]`, `UNSUPPORTED_LABELS`) and the fixed `UNSUPPORTED_REPLY` in the chat, its `InboundMessage` (`replied`) and the reply in the outbox, in one transaction, then sends it (every type that isn't text, reactions and `system` notices too); the customer's real ChatSession (or a new one); one transaction saves the customer message with an `InboundMessage` row (configuration-service's `chat_app.InboundMessage`, unique Meta `message_id`, `received` → `replied`) so duplicates are answered once and a redelivery after a failure doesn't save the message twice (`flow.handle_customer_message(..., save_message=False)`, `flow.append_in_transaction`); errors raise → nack. The transaction saving the turn's messages also marks the row `replied` and puts them in the **outbox** (configuration-service's `chat_app.OutboundMessage`; see **Outbox**), which then sends them on WhatsApp through configuration-service's internal send endpoint (`app/whatsapp_sender.py`: `POST {CONFIGURATION_SERVICE_URL}/internal/whatsapp/{business_id}/send/`, `X-Internal-Api-Key`; configuration-service holds the token), retrying failures. Locally, `../mock_whatsapp` plays WhatsApp both ways.
- **The chat flow** (the user asked: moved from configuration-service's `chat_app`, the parts that need the LLM): `POST /api/chat/sandbox-sessions/{pk}/messages/` (the frontend's Chat Sandbox, login required) and `POST /api/chat/sessions/messages/` (a customer message, public). **Same paths, status codes and JSON bodies as Django** (DRF-style errors), so callers only change the host. They were removed from configuration-service (the user asked), with its `ollama` dependency: **`app/chat_flow` is the only copy**. Listing chats, sandbox sessions (create / delete), the chat settings and answering questions stay in configuration-service.

The sibling services are `../configuration-service` (Django, port 8000) and `../frontend-app` (Vite/React, port 5173). The user named the folder "messaing-service"; it was created as `messaging-service`, assumed to be a typo. It was first built with Flask + flask-smorest and later ported to FastAPI (the user asked), keeping the same endpoints, status codes and error bodies.

- **The database belongs to configuration-service (the user's rule): no migrations here, ever.** This service only queries rows and writes them where the chat flow needs it (chat messages, chat state, orders, bookings and their calendar letters, unanswered questions). Never create, alter or drop tables, add Alembic, or `create_all()` against PostgreSQL (tests do it on SQLite only). A schema change is a Django migration in configuration-service first, then the mapping in `app/models.py`; `tests/test_schema.py` (CI's `schema` job, on a Django-migrated PostgreSQL) checks they match. Django's defaults and signals don't run here: inserts set every column (e.g. `payment_reference`, times), and placing a booking paints its provider's week (`schedule.sync_booking`).
- Add dependencies to `requirements.txt` with a version range. FastAPI is pinned to a minor version (`<0.143`) because 0.x minors can break things.

## Structure and conventions

- `app/llm.py`: `get_client()` is a lazy, shared `ollama.Client(host=OLLAMA_HOST, timeout=…)`. `generate_reply(prompt)` sends `[system: SYSTEM_PROMPT, user: prompt]` to `OLLAMA_MODEL` and returns `response.message.content`. It maps failures to its own exceptions, which `app/chat.py` turns into HTTP errors:
  - `ConnectionError` → `LLMUnavailableError` → **503**.
  - `httpx.TimeoutException` → `LLMTimeoutError` → **504**.
  - `ollama.ResponseError` (e.g. model not pulled) → `LLMError` → **502**.
- `app/chat.py`: router tagged `chat`, `POST /chat` → `ChatResponse {reply, model}`. **Stateless**: no history is kept between requests. Multi-turn chat would need a request schema with `messages` and, probably, storage; that's not built yet. It's a plain `def`, so FastAPI runs the blocking Ollama call in a thread pool; keep blocking routes as `def`, not `async def`.
- `app/routes.py`: router tagged `main`, `GET /`.
- `app/consumer.py`: `parse(data)` (JSON object with `business_id`, `message_id`, `from`, `type`, else `InvalidMessageError`), `process(payload)` (log + sleep: replace with the real work), `handle(message, stats)` (malformed → ack + `skipped`; `process` raised → nack + `failed`; else ack + `handled`), `ensure_emulator_resources()` (emulator only: topic + ordered subscription, `AlreadyExists` ok, retries), `Consumer` (`start(emulator)` / `stop()`, `running`, `stats`). Dedup on `message_id` is a TODO for when there's real work.
- **Retries and dead letters** (the user asked; docker-compose's `pubsub-init` creates the subscriptions: ack deadline 120 s here / 60 s for processing-service's, retry backoff 30–600 s, 5 delivery attempts, then the dead-letter topics `whatsapp-inbound-messages-dlq` / `payment-events-dlq`, each with a `…-dlq-sub` subscription to look at them). **Test endpoints** (the user asked, to try them; `app/consumer_routes.py` `test_router`, mounted only with `PUBSUB_TEST_ENDPOINTS_ENABLED`): `POST /consumer/test/nack` / `POST /consumer/test/no-ack` (202 `ConsumerTestMessage`; 503 if publishing fails) publish a message with the attribute `test_behavior` (`consumer.publish_test_message`); `consumer.handle` sends those to `handle_test()` before parsing (not counted in the stats): `nack` sleeps `PUBSUB_TEST_NACK_DELAY_SECONDS` then nacks, `no_ack` calls `message.drop()` (no ack / nack and no more lease extensions, like a crash; returning without it, the client would keep extending the lease for up to an hour); both log the `delivery_attempt`. Tests: `TestMessageTests`, `TestEndpointsTests` in `tests/test_consumer.py`.
- `create_app(consumer=None)`: builds a `Consumer()` when `PUBSUB_CONSUMER_ENABLED`; the lifespan (`lifespan_for`) starts it (in the thread pool; with the emulator when `PUBSUB_EMULATOR_HOST` is set) and stops it on shutdown. Each Gunicorn worker runs one; they share the subscription. Tests pass a `Consumer` with fake clients. `app/consumer_routes.py`: `GET /consumer` → `ConsumerStatus`.
- `app/latency.py` (the user asked): latency logs, logger `app.latency`, INFO lines `[LATENCY][TAG][TAG…] 1.234s key=value…` (tags broad → specific, so a search for e.g. `[LATENCY][LLM][ORDER_STATUS]` finds one route). `bind(channel, chat, msg)` adds fields to every line inside it and collects the stages for `summary()`; `timed(*tags, **fields)` times a block (`status=error` if it raised); `add_fields()` only inside a bind. Logged: `E2E` + `SUMMARY` per message (`consumer.process`: from receipt until the last WhatsApp reply was sent; `chat_api._run_turn`: per request, channel `sandbox` / `api`), `PUBSUB` (wait since publish), `TURN`, `DB` `LOAD` / `COMMIT_TURN` (only when placing an order / booking) / `SAVE_TURN` / `ORDER_STATUS` `LOOKUP`, `LLM` `ROUTER` / `EXTRACTION` `<STEP>` / `QUESTION_CHECK` / `ORDER_STATUS` `EXTRACTION` / `REPLY` / `ASIDE` / `REPLY`, `TOOL` `<NAME>`, `PAYMENT`, `SEND`. Add new stages with `timed()` at the call site, keeping the tag scheme. Tests: `tests/test_latency.py`.
- `app/errors.py`: exception handlers that keep the old flask-smorest error shapes. Every `HTTPException` (including 404/405) → `{code, status, message}`. `RequestValidationError` → `{code: 422, status, errors: {<location>: {<field>: [msg, ...]}}}`, where FastAPI's `body` location is renamed `json` (so `errors.json.prompt`), and a whole-body error (e.g. not a JSON object) goes under the field `_schema`. `status` is `http.HTTPStatus(code).phrase`; on Python 3.13+ that's "Unprocessable Content" for 422 (werkzeug said "Unprocessable Entity").
- **The chat flow, `app/chat_flow/`**: each module is a copy of its `chat_app` namesake (`constants`, `validators`, `prompts`, `router`, `order_flow`, `flow`, `tools`, `past_orders`, `questions`: only `ask_business`) plus ports of what they used from Django: `checkout.py` (`checkout_app/services.py` `place_order` / `place_booking` + `checkout_app/validators.py` + `ScheduleItem.clean`), `schedule.py` (`checkout_app/schedule.py`: free times, `start_problem`, `sync_booking`), `stock.py` (derived quantities), `settings.py` (`ChatSettings.for_business` = `ChatConfiguration.for_business`), `emails.py` (Django's `EmailValidator`, checked identical), `dates.py`, `errors.py` (`ValidationError`). Changes from Django are only mechanical: functions that query take a session `db`; the flow takes a `sessionmaker` and **reads in short sessions** (closed before LLM calls, like Django's autocommit) and **writes in transactions** (`sessions.begin()`; `append_chat_message`, `commit_turn` with `begin_nested()` savepoints around `place_order` / `place_booking`, `ask_business`); `SELECT … FOR UPDATE` as in Django; JSON columns are reassigned, never mutated. The LLM calls are in `app/llm.py` (`generate_structured`, `generate_chat_reply`).
- `app/chat_api.py`: the two endpoints. Checks in Django's order: login (`app/auth.py`: SimpleJWT's 401 bodies: not provided / `token_not_valid` / `user_not_found` / `user_inactive`, `WWW-Authenticate: Bearer realm="api"`), then no business 403 / unknown 404 / other business 403 / not sandbox 400, then the body (`app/drf.py`: DRF `CharField` / `IntegerField` rules and messages, e.g. `{"message": ["This field may not be blank."]}`); LLM errors → 502 / 503 / 504 `{"detail": …}`, a chat that kept changing during the turn (`flow.ChatConflictError`) → 409. The turn runs in the thread pool. `get_sessions()` is a dependency (tests override it).
- **Concurrent changes** (the user asked, after burst messages raced: missing context, overwritten state, replies out of order): **`ChatSession.version`** (configuration-service's column; Django's `save()` adds 1 with `F()`) is mapped as SQLAlchemy's `version_id_col` (`app/models.py`: every UPDATE adds 1, a new chat starts at 0), so every change in either service raises it. A turn (`flow._run_turn`) reads the version with the chat, runs the LLM work, then saves the state, the welcome message and the reply **in one transaction at the end** (`flow.save_turn`, row locked by `order_flow.lock_session`), only if the version is still the one read; else `order_flow.ChatChanged`, nothing of that attempt is saved, and `handle_customer_message` runs the whole turn again on the fresh chat (the customer message isn't saved again), up to `TURN_ATTEMPTS_MAX`, then `flow.ChatConflictError` (API 409; the consumer nacks). Placing an order / booking can't wait for the reply (it needs the number and payment link): `order_flow.commit_turn(..., version=)` checks the version when placing (a change → the turn runs again, nothing placed) and returns the new one; after that the turn can't run again (it would place twice), so a change during the aside / reply is only logged and the reply saved. `debug.attempts`. The question check's `ask_business` still saves on its own (a rerun gets `already_asked`). With WhatsApp, the subscription has no message ordering (the user asked, for **one reply to messages sent close together**: `app/inbound.py` step 4): a customer's messages are handled in parallel, each saved as it arrives; a turn answers every customer message since the business's last one (`flow.pending_text`, also what the question check reads), and its save marks every `received` InboundMessage of the chat `replied` (only its own if the chat changed after it read it: `save_turn`'s `saw_all`, false only for a turn that placed an order / booking); `handle_customer_message(before_attempt=)` stops a turn whose message was answered meanwhile (`stop_if_answered`, no LLM call). The welcome message goes to a chat the business hasn't written in yet. Each WhatsApp message is put in the order it was sent (`flow.add_message(sent_time=)`, Meta's timestamp, which becomes its `message_time`) among the unanswered customer messages at the end; never before the business's last message (a late one goes right after it) and never after now; same-second ties keep arrival order; the Chat Sandbox (no timestamp) appends at now; a time is never before the message it follows (another clock a little ahead), and an unreadable stored time just appends. A non-text message's placeholder and fixed reply arriving among unanswered messages are moved before them in what the turn reads (`flow.conversation`: `to_llm_history`, `pending_text`; nothing is dropped, so `history_start` positions still line up). In the Chat Sandbox, a message left unanswered (e.g. the LLM was down) is answered with the next one, and the welcome goes to a chat the business hasn't written in. Known limits: a turn sees the last `HISTORY_MAX_MESSAGES` (20), but marks every waiting message replied; a cancel's `history_start` is its turn's last message, so in a burst like "new order: 2 kopi" + "cancel the old one" the first message's items are missed. Every message of a burst runs its own turn in parallel (extra LLM calls; only one reply is kept). The version catches the rest (the Chat Sandbox / API, the business answering in configuration-service, redeliveries). Tests: `tests/test_inbound_bundling.py`, `tests/test_chat_concurrency.py`.
- **Outbox** (the user asked, so a reply is never lost when sending fails; `app/outbox.py`, configuration-service's `chat_app.OutboundMessage`): `inbound.handle_inbound` passes `flow.handle_customer_message(..., on_saved=)` a hook that `flow.save_turn` calls **inside its transaction**, after adding the turn's messages: it locks the `InboundMessage` row and, if it's already `replied` (another worker answered a duplicate meanwhile), raises `inbound.AlreadyReplied` so the whole save rolls back and nothing is sent (`skipped`), unless this turn placed an order / booking (`placed`, from `turn.placed_order_id` / `placed_booking_id`: really placed, not only tried; its confirmation and payment link are still queued, with a warning); else marks it `replied` and adds one `pending` row per message (welcome, reply; flushed one by one so ids follow the send order). After the turn, `outbox.send_due(sessions, chat_session_id=)` sends that chat's due rows (a failure there is only logged: the sweeper retries). `send_due` takes the next due row with no earlier `pending` row in its chat (`due_query`: oldest first, `FOR UPDATE SKIP LOCKED`, so concurrent workers never send the same row), one transaction per row with the row locked during the send: sent → `sent`, `meta_message_id`, `sent_time`; any exception → `attempts` + 1, `last_error`, `next_attempt_time` = the current time (not the round's) + `OUTBOX_RETRY_DELAYS_SECONDS[attempt]` (10 s, 30 s, 120 s, then 600 s), `failed` at `OUTBOX_ATTEMPTS_MAX` (5, an ERROR log), or at once for a permanent refusal (`whatsapp_sender.SendError.permanent`: configuration-service's 4xx except 401 / 403 / 408 / 429, i.e. 400 / 404). A pending row (retrying) holds back its chat's later rows; a `failed` one doesn't. The **sweeper**: `Consumer` runs a daemon thread calling `send_due` for every chat each `OUTBOX_SWEEP_SECONDS` (env, 30; 0 = off; `Consumer(sweep_seconds=)` in tests), stopped by `stop()` (a new stop `Event` per `start()`). Sending is at least once (a worker dying after Meta accepted, before `sent` is saved, sends again); the Chat Sandbox and the customer API don't use the outbox (no WhatsApp). Tests: `tests/test_outbox.py`, `tests/test_inbound.py`.
- **Tests** (`python -m unittest -v`) use `fastapi.testclient.TestClient(create_app())` and never call a real model or Pub/Sub (`tests/test_consumer.py`: `FakeMessage`, `MagicMock` subscriber / publisher; `time.sleep` patched). They patch `app.llm.get_client` with a `MagicMock` whose `.chat` returns `SimpleNamespace(message=SimpleNamespace(content=...))`, or raises one of the errors above. Keep new LLM-dependent tests mocked. The chat flow tests (`tests/test_chat_*.py`) were ported from `chat_app`'s and `checkout_app`'s tests (removed there with the flow): `tests/chat_helpers.py` (`DatabaseTestCase`: a fresh SQLite file per test with `create_all` and SAVEPOINTs enabled, `self.make` factories, `self.get` / `self.all`; `ApiTestCase`: `self.client`, `self.login(user)` with a token signed by `TEST_SIGNING_KEY`; `FlowTestMixin` + the fake LLM, as in Django) and `tests/schedule_helpers.py` (`open_week`, `book`, `day_letters`…).
- Every endpoint needs typed request/response models, a `summary=` and (where useful) a docstring (it becomes the Swagger description), plus `responses=` entries for its error codes, so it shows up usefully in `/docs`. Document 422 with `ValidationErrorResponse` and other errors with `ErrorResponse`, since FastAPI's default 422 schema doesn't match the real body.

## The chat flow in detail (`app/chat_flow`)

Moved from configuration-service's CLAUDE.md with the code (the user asked to remove the flow there). Written for `chat_app`: the module names map one to one (`chat_app/flow.py` → `app/chat_flow/flow.py`, `checkout_app.services.place_order` / `place_booking` → `app/chat_flow/checkout.py`, `checkout_app.schedule` → `app/chat_flow/schedule.py`, `ChatConfiguration.for_business` → `settings.ChatSettings.for_business`, the LLM calls → `app/llm.py`), the endpoints are `app/chat_api.py`, the WhatsApp consumer runs it through `app/inbound.py`, and the tests are `tests/test_chat_*.py` (ports of the Django tests named here).


The user asked for a **router + sub-flows** design (replacing the user-built block graph): the flow is fixed in code, each business only configures its steps (`ChatConfiguration`), and each sub-flow is a small deterministic state machine. Per customer message, `flow.handle_customer_message()`:
1. Saves the message (`append_chat_message`).
2. **Routes** (`router.route_message`): one `llm.generate_structured` call (`prompts.ROUTER_SCHEMA` `{intents: [..]}`, temperature 0) with `build_router_prompt()` (business name + description, product names, where the order is: none / in progress at step X / already placed #N). `intents` ⊆ `constants.INTENTS`: `order`, `booking`, `question`, `order_status` (past orders or bookings), `off_topic`, `cancel` (stop the order / booking in progress; several allowed; empty for greetings/thanks); `router.clean_intents()` keeps known ones, once, in `INTENTS` order. `Route` exposes `start_order`, `start_booking`, `cancel`, `question`, `order_status`, `off_topic`, `only_order_status`. **Leaving a branch** (the user asked: a chat in an order couldn't get to a booking; `order_flow._leave_branch`, before any extraction): `cancel` drops the order / booking in progress (back to `start`, keeping `last_order_id` / `last_booking_id`, no extraction); asking for the other branch switches over if nothing was chosen (`BRANCH_PROGRESS_KEYS`: items / details, service / slot / details) and the current branch's intent is absent, else it's `held_back` (stays; the reply says finish or cancel first); cancel + the other branch starts it on the same message, the same branch never; cancelling saves `history_start` (the cancelling message's index in `chat_message_json`, in both services' `validate_chat_state_data`) and the steps' extractions only read from there (`_steps_history`, `advance(message_count=)`) until one is placed, so a cancelled cart can't come back. `Turn.cancelled` / `switched_from` / `held_back` → `prompts.branch_change_sections` in the reply and aside prompts (an aside also for template steps); a `cancel` with nothing in progress gets a section saying never to claim anything was cancelled. Tests: `tests/test_chat_switching.py`. **Code, not the model, picks the handlers.**
3. **Order sub-flow** (`order_flow.advance(chat_config, step, data, history, products, start_order=)`): Product selection → Details collection → Confirmation (`ORDER_STEPS`, `NEXT_STEP`). At `start` nothing runs unless `start_order` (then Product selection runs on the same message). **While an order is in progress, its steps run on every message whatever the router says** (short replies like "Alice" carry no intent), unless it's cancelled or the other branch is asked for (**Leaving a branch**, under Routes). After the order is placed (`completed`), no extraction. Unknown steps fall back to `start`.
   - **Extract** with `llm.generate_structured(system_prompt, history, schema)`: Ollama `format=<JSON schema>`, `STRUCTURED_OPTIONS` (temperature 0); invalid JSON → `LLMError` (502). Schemas come from `prompts.extraction_schema(step, fields, go_back)` (static `EXTRACTION_SCHEMAS`, except the details steps, built from the branch's detail fields), task prompts from `_EXTRACTION_TASKS`: Product selection `{items: [{product_id, quantity|null}], done_choosing}`, Details collection one nullable key per field (`number` fields typed as numbers), Confirmation `{decision: confirm|change|none}`.
   - **Check deterministically** with `order_flow.CHECKS[step](extracted, data, products, fields) → CheckResult(complete, missing, issues, go_back)`, updating `chat_state_data` in place. Never trust the LLM's values: products must be the business's active ones (`tools.active_products`) with 1 ≤ quantity ≤ `quantity_available` (`order_flow.item_problem()`: sold out (0 available) comes first, "has run out"); the cart kept from earlier messages is re-checked against current stock on every message, and items that can't be ordered any more are dropped (with an issue, so `items_confirmed` is cleared) (the user asked); Product selection then waits for the customer to confirm the cart (the user asked: recap, "anything else?", only then details): it completes only if `done_choosing` is true **and** the cart (`_cart()`: (product_id, quantity) pairs) didn't change in that message, or `items_confirmed` is already set; a changed cart clears `items_confirmed`; details go through `order_flow.clean_detail_value()` by type (text `max_length`, number parse + bounds, `EmailValidator`; no phone type: customers chat on WhatsApp, so the chat has their number); known details are kept when the LLM returns null; ints exclude bools. Complete → the next step, and the loop runs again there (bounded by `MAX_STEPS_PER_MESSAGE`), so one message can pass several steps. `change` at Confirmation → back to Product selection (data kept, so complete steps pass straight through). A Confirmation reached in the same message is not extracted (the customer hasn't seen the summary). **Confirmation substages** (the user asked, after the LLM told a customer "your order is confirmed" before anything was saved): `not_confirmed` (the chat sends the summary, a fixed template, and waits; anything but a clear "confirm" (`_EXTRACTION_TASKS[confirmation]` is strict: "no, nothing else" is `none`) re-sends it) → `confirmed` (the order is saved in `commit_turn()`, **then** the fixed confirmation message is sent; the chat goes straight back to `start` with `chat_state_data = {last_order_id}`, so the customer can order again). `confirmed` only exists within that turn (`Turn.confirmation_status`, `debug.confirmation`); a saved chat at `confirmation` is always `not_confirmed`. After an order, `start` + `last_order_id` (the router and reply prompts mention it); a new order starts from scratch.
   - **Going back** (the user asked: back to a specific earlier step, without losing data): `order_flow.GO_BACK_TARGETS` (Details collection → `product_selection`; Confirmation → `product_selection`, `details_collection`); `extraction_schema(..., go_back)` adds a required `go_back_to` (enum | null) and `build_extraction_prompt(go_back=)` a "Going back" section. A valid `go_back_to` (before the step's check) moves there, keeps `turn.data` (except: target Product selection drops `items_confirmed`), records a step with `go_back_to`, sets `Turn.went_back_to`, and continues there on the same message. Only offered at the step the chat was at when the message arrived (`entered_now` false): a step reached during the turn gets none, because the message that completed the earlier step would read as "go back" (a real bug). So at most one go-back per turn. The reply prompt gets `went_back=True` when the turn ended on that target.
4. `order_flow.commit_turn()` writes `chat_state_id` / `chat_state_data` (validated) and fills an empty `display_name` from `details.name`. Saved with the reply at the end of the turn (`flow.save_turn`, version checked), or at once when placing an order / booking (see **Concurrent changes**).
5. **FAQ handler** (`check_customer_question`, below), only if the router found a `question`.
6. **Reply.** **At Confirmation the reply is always a fixed template** (the LLM must never decide what's confirmed): `prompts.confirmation_request_message(data, labels)` (summary: items, total, details, then "Please reply CONFIRM…") while `not_confirmed`, or `prompts.order_confirmed_message(business, order_id, data, labels)` once the order is saved. If the message also has a question (answered / unanswered), an order status request or an off-topic part, `prompts.build_aside_prompt()` (the intro rules + "the summary / confirmation is sent automatically: don't summarise or say anything about it being confirmed", no order data) gets a short LLM aside, put before the summary request or after the confirmation. `debug.reply_kind`: `llm` / `order_status` / `order_status_fallback` / `order_status_not_found` / `confirmation_request` / `order_confirmed` / `slot_options` / `booking_confirmation_request` / `booking_confirmed`. **Order status branch** (the user asked: customers check their own past orders and bookings; first built with tools, then, after a small model made up bookings when a tool said "not found", the user asked for this): **no tools, no states**. Whenever the router finds `order_status`, `flow.check_order_status()`: 1. one `llm.generate_structured` call (`prompts.ORDER_STATUS_SCHEMA` `{kind: order|booking|any, numbers: [int]}`, `build_order_status_extraction_prompt`: "never make up a number"), made safe by `past_orders.clean_request()` (unknown kind → any; positive ints, "#12" ok, once, ≤ `NUMBERS_MAX` 5); 2. `past_orders.lookup(session, kind, numbers, now)`, plain code, **only among the customer's own** (`customer_sessions(session)`: same business, same phone number, real or sandbox like the chat; sandbox chats without a phone number are one test customer, so a test order can be checked from another test chat (the user asked)): numbers → their orders / bookings with that number (both tables if `any`; the other kind too if not of the kind asked: customers mix the words up), else "not found" (`Lookup.not_found`, the same whether or not someone else has it); no numbers → their orders / bookings newest first (≤ `LIST_MAX` 10); records (`order_record` / `booking_record`) with `status` (Payment pending / Payment received / Completed) and `status_meaning`; 3. `prompts.format_order_records(found)` = the only facts. With other intents, `prompts.order_status_section(records)` goes into the reply / aside prompt (`order_records=`; not grounding-checked). `debug.order_status` = `{extracted, system_prompt, records, found}` (null when not asked). Tests: `tests/test_past_orders.py` (scope, lookup, clean_request, grounding, the records text and fallback, no order tools) and `RouterFlowTests` in `tests/test_flow.py` (the fake LLM answers the extraction via `order_status=`; `is_order_status_check`). Otherwise `llm.generate_chat_reply(system_prompt, history, toolbox)` with `prompts.build_reply_prompt(business, step, data, products=, fields=, missing=, issues=, finished=, went_back=, intents=, question_check=)`: business info, step + goal (`STEP_GOALS`; `start` = no order in progress), collected data with a Python-computed total, details to collect, still-needed list, issues, catalog for `start` / Product selection, the question section, an order status section (`order_status` intent: `order_status_section(records)`, the customer's records looked up) and an off-topic section (`off_topic` intent: decline that part politely), then per-step `_REPLY_INSTRUCTIONS` (not Confirmation: templates). ## Environment notes for Claude

- **Ollama can't be reached from the sandbox.** All HTTP goes through the Apple Claude Code proxy. A request to `localhost:11434` (or any closed port) comes back as a proxy **502**, not a `ConnectionError`, so a live `/chat` call returns 502 with an "ACC Proxy" message. That's the sandbox, not the app. **Don't bypass the proxy** (e.g. `curl --noproxy`), which is blocked by policy. The user tests with the real LLM themselves; rely on the mocked unit tests.
- `python run.py` starts uvicorn, but binding the port fails here (`operation not permitted`). Use FastAPI's `TestClient` instead.
- compose's PostgreSQL (`localhost:5433`) is sometimes unreachable from the sandbox; the tests don't need it (SQLite).
- The user's shell sets `PYTHONPATH` to a Spark install, so `pip freeze` shows `pyspark`. Don't add it to `requirements.txt`.
