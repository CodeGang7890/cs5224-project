# payment-ingester

Not built yet (see `TODO.txt`). It will receive Xendit's payment webhooks and publish each payment event to Pub/Sub for processing-service, on port **8001** (reserved).

For now there's a standalone script that publishes dummy payment events to the local Pub/Sub emulator.

## Pub/Sub message contract

| | |
| --- | --- |
| Topic | `payment-events` (created by docker-compose's `pubsub-init`) |
| Data | JSON `{"payment_reference": "3f9c1a2b4d5e6f708192a3b4c5d6e7f8", "status": "success"}`: the order's / booking's `payment_reference` (128-bit, 32 hex characters, generated by configuration-service) and `status` `success` or `fail` |
| Attributes | `payment_reference`, `status` |

## Publishing dummy payment events

With the stack running (`docker compose up --build`, from the repository root):

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt   # once
.venv/bin/python scripts/publish_dummy_payments.py                  # up to 5 random pending orders / bookings
.venv/bin/python scripts/publish_dummy_payments.py --count 20
.venv/bin/python scripts/publish_dummy_payments.py --status fail    # all failed payments
.venv/bin/python scripts/publish_dummy_payments.py --reference <32 hex characters>   # a given reference (repeatable)
```

The script uses the emulator at `PUBSUB_EMULATOR_HOST` (default `localhost:8085`), never Google Cloud. `GCP_PROJECT_ID` (default `local-project`) and `PUBSUB_TOPIC` (default `payment-events`) can be overridden.

By default the script reads the payment references of orders and bookings still pending payment from configuration-service's PostgreSQL (`localhost:5433`; `POSTGRES_*` override it), picks some at random, and gives each a random status. processing-service pulls the events and applies them: `docker compose logs -f processing-service`.
