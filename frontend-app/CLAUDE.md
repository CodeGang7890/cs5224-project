# CLAUDE.md: frontend-app

Guidance for Claude Code when working in `frontend-app/`.

## What this is

**Ansera Business Admin**: a **client-side-only React SPA**. There is no SSR, no React Server Components, no Next.js/Remix and no framework mode. Don't add server-rendered patterns, `"use client"`/`"use server"` directives, or server-only APIs.

## Stack (keep to these; don't swap libraries without asking)

| Concern | Library | Notes |
| --- | --- | --- |
| Build | **Vite 8** | Not CRA. Config in `vite.config.ts` (React plugin + `@tailwindcss/vite`, `@` → `src` alias). |
| Language | **TypeScript 6** (strict-ish) | `verbatimModuleSyntax` is on, so use `import type` for type-only imports. Don't use `baseUrl` (deprecated in TS 6); `paths` alone defines the alias. |
| UI | **React 19** | Function components + hooks only. |
| Routing | **React Router v8** | Data router: route table in `src/app/routes.tsx`, `createBrowserRouter` in `src/app/router.tsx`, `RouterProvider` from `react-router/dom`. The URL is the source of truth: tabs are `NavLink`s, and UI such as modals that should survive refresh or back use search params (e.g. the profile modal uses `?profile`). Import hooks/components (`Link`, `NavLink`, `Outlet`, `useParams`, …) from `react-router`, **not** `react-router-dom`. |
| HTTP | **Axios** | Use `configurationApiClient` from `@/lib/api-client`, never bare `axios` or `fetch`. It calls the `configuration-service` API root (`VITE_CONFIGURATION_SERVICE_URL`, default `http://localhost:8000/api`) and handles JWT refresh and DRF errors. The Chat Sandbox also calls this API; configuration-service forwards its message to private messaging-service. Paths are relative to `/api` and Django URLs end with `/`. |
| Server state | **TanStack Query v5** | All API data fetching goes through `useQuery`/`useMutation` for loading/error/caching. Use each feature's query-key factory (e.g. `postKeys`). Client config: `@/lib/query-client`. Devtools render in dev only. |
| Client state | **Zustand v5** | Only for client/UI state (theme, UI toggles, auth token, etc.). **Never** copy server data into Zustand; that's TanStack Query's job. Stores live in `src/stores/`, one per concern, named `use<Name>Store`. Select narrow slices: `useStore((s) => s.x)`. |
| Styling | **Tailwind CSS v4** | CSS-first config (no `tailwind.config.js`). Theme tokens are CSS variables in `src/index.css`. Dark mode uses the `.dark` class on `<html>`, set by `useApplyTheme`. |
| Components | **shadcn/ui** (Radix, `new-york` style, neutral) | Config in `components.json`. Components live in `src/components/ui/`. Add with `npx shadcn@latest add <name>`. Use the `cn()` helper from `@/lib/utils` to merge classes. Icons: `lucide-react`. |
| Workflow diagram | **React Flow** (`@xyflow/react` v12) | Read-only node/edge diagram for `features/workflow`. Import its CSS once (`@xyflow/react/dist/style.css`, done in `workflow-editor.tsx`). Pass `colorMode` from the theme store. Keep `nodeTypes`/`edgeTypes` objects at module level. |
| Lint | **oxlint** | `npm run lint`. Config in `.oxlintrc.json`. |

## Project structure conventions

- `src/app/`: app shell. `routes.tsx` is the route table (plain `RouteObject[]`, importable without a browser); `router.tsx` wraps it in `createBrowserRouter`; `providers.tsx` holds global providers.
- `src/config/`: `app.ts` (`APP_NAME`), `navigation.ts` (`paths`, top-nav `navItems` (`requiresAuth`), each section's sub-tabs `catalogTabs` / `ordersTabs` / `chatsTabs`, and `legacyRedirects`; use `paths` instead of hard-coded URLs), `env.ts` (typed env access).
- **Adding a page**: create `src/pages/<name>-page.tsx`, add its path to `paths`, add a route in `routes.tsx`, and add it to `navItems` if it's a top-nav tab (`requiresAuth: true` hides it while logged out), or to a section's sub-tabs (then route it as a child of that section's layout route, and wrap it in `TabPage`, `@/components/common/tab-page`, which sets the title `<sub-tab> · <section> | APP_NAME`). Pages set the browser tab title by rendering `<title>{`${title} | ${APP_NAME}`}</title>` (React 19 hoists it into `<head>`); `PagePlaceholder` does this already.
- `src/pages/`: route-level components. Keep them thin; they compose features. **Tabs** (the user asked to group them, there were too many): Home `/` (WhatsApp card (`features/whatsapp`) and random-number card, public) and Workflow `/workflow` (the fixed chat flow and its settings), then three sections, each a layout route (`catalog-page.tsx`, `orders-page.tsx`, `chats-page.tsx` → `SectionLayout`, `@/components/layout/section-layout`: heading + sub-tab `NavLink`s + `<Outlet />`) whose sub-tabs are child routes (so each keeps its own `?page=` / filters in its own URL); the section's index route redirects to its first sub-tab (`SectionIndexRedirect`, `@/components/common/redirects`):
  - **Catalog** `/catalog`: Products `/catalog/products` (CRUD), Services `/catalog/services` (services, providers, schedules), FAQs `/catalog/faqs` (CRUD).
  - **Orders** `/orders`: Products `/orders/products` (orders), Services `/orders/services` (bookings), Payment `/orders/payment` (placeholder).
  - **Chats** `/chats`: Conversations `/chats/conversations`, Unanswered questions `/chats/questions` (red count badge on the sub-tab while any are open), Chat Sandbox `/chats/sandbox` (test chats with the assistant as a pretend customer).
  - **Everything but Home is behind `RequireAuth`, and its top-nav tabs are hidden while logged out** (the user asked; `RootLayout` filters `navItems` by `requiresAuth`); a typed-in URL still shows the login guard (the section layouts are inside the guard too, so nothing of the page shows).
  - **Old URLs redirect, keeping their query string:** `/product`, `/service`, `/faq`, `/payment`, `/chat-sandbox` (`legacyRedirects` → `RedirectKeepingSearch`), and `/orders?tab=services…` / `/chats?tab=questions…` (`SectionIndexRedirect`'s `legacyTabs`, dropping `tab`).
- `src/features/<feature>/`: self-contained domain modules with `api/` (Axios functions), `hooks/` (TanStack Query hooks + keys), `components/`, `types.ts`, and an `index.ts` public API. Import features via `@/features/<feature>`, not their internal paths. `features/random-number` is the reference example for the Axios + TanStack Query pattern: it calls `GET /api/configuration/random-number/` on configuration-service and is shown on the Home page. `features/auth` holds the login dialog, auth API calls and the `useAuth` / `useCurrentUser` hooks. `features/products` and `features/faqs` implement CRUD (see "CRUD pattern" below). `features/chat-sessions` holds the chat session API calls and the Chat Sandbox (see "Chat Sandbox" below). `features/workflow` is the chat flow diagram + configuration editor (see "Workflow editor" below). `features/orders` is the read-only Orders tab (see "Orders tab" below). `features/services` is Catalog → Services (see "Catalog → Services" below). `features/questions` is the Chats tab's Unanswered questions sub-tab (see "Chats tab" below). `features/profile` holds the profile modal (`ProfileDialog`), which shows `useCurrentUser()` data. `features/whatsapp` is the WhatsApp connection card (see "WhatsApp card" below).
- `src/components/ui/`: shadcn-generated code. Prefer composing or wrapping over heavy edits. The oxlint `only-export-components` rule is disabled for this folder.
- `src/components/layout/`: layout components. `RootLayout` renders the sticky header (app name, nav tabs, theme toggle, `AuthControls`) and the `<Outlet />`. `AuthControls` lives in layout, not in a feature, because it combines `features/auth` and `features/profile`; this avoids a circular import.
- `src/components/common/`: shared app-level components that aren't shadcn primitives (e.g. `PagePlaceholder`).
- `src/lib/`: shared singletons/utilities (`createApiClient` + service clients, `queryClient`, `cn`).
- `src/stores/`: Zustand stores. `src/hooks/`: shared hooks. `src/types/`: shared types.
- File names are **kebab-case** (`random-number-card.tsx`, `use-random-number.ts`), matching shadcn. Exports are named (no default exports).
- Always import from `src` via the `@/` alias.

## CRUD pattern (`features/products`, `features/faqs`)

Copy this structure for new CRUD features.

- **Files:**
  - `types.ts`: the API shape, plus an `*Input` type with **only the writable fields**.
  - `validation.ts`: limits mirrored from the Django models, `validate*()`, `changed*Fields()` (a diff for PATCH), and the form ↔ API converters. Number fields are kept as strings in form state.
  - `api/`: `list(page)`, `create`, `update(id, changes)` (PATCH), and `delete`.
  - `hooks/`: `*Keys`, `use*(page)` with `keepPreviousData`, and `useSave*`/`useDelete*`, which invalidate `*Keys.all` on success.
  - `components/`: `*Manager` (the list), `*FormDialog` and `Delete*Dialog`.
- **Field rules (from configuration-service):**
  - Never send `id` or `business`; the backend fills in the user's business.
  - Product stock: only `total_quantity` is stored and editable (the user asked). `quantity_available`, `quantity_on_hold` and `quantity_sold` are derived by the backend from the orders: display them, but never send them, or the API returns 400. When editing, `total_quantity` can't go below on hold + sold (`minTotalQuantity()` in `validation.ts`, checked client-side and by the backend); the form shows them in `StockSummary` with a live "after saving: N available". The table shows Total / Available ("Sold out" at 0) / On hold / Sold.
  - Editable: product `name`, `description` (≤300: what the chat assistant tells customers the product is), `information` (≤5000: extra details the assistant looks up for specific questions; both explained by tooltips in `ProductFormDialog`), `price` (a decimal string, sent with `toFixed(2)`), `total_quantity`, `is_active`; FAQ `question`, `answer`.
  - If the backend limits change, update `PRODUCT_LIMITS` / `FAQ_LIMITS`.
- **Flow:** submit → client validation → `ConfirmDialog` (`@/components/common/confirm-dialog`) → mutation. The confirm dialog stays open with a pending state until the request finishes. On a 400, `getFormErrors()` (`@/lib/form-errors`) maps DRF `{field: [msg]}` errors onto fields, and `non_field_errors` becomes the form alert. **Every save and every delete must go through `ConfirmDialog`** (the user asked for this).
- **Form state:** the form content is remounted on each open (`{open && <Form />}`), so it always starts from the saved values. Edit mode sends only the changed fields, and **Save** is disabled when nothing changed.
- **Pagination:** `usePageParam()` keeps `?page=` in the URL, and `PaginationControls` renders the controls. If a page goes out of range (the API returns 404, e.g. after deleting the last item), the manager steps back a page.
- **Shared components:** `FormField` (label, optional `tooltip` (an (i) `InfoTooltip`, `@/components/common/info-tooltip`, built on `components/ui/tooltip`), hint/error, character counter) and `components/ui` `alert-dialog`, `table`, `textarea`, `switch` and `badge`. These were hand-written from shadcn because the CLI is blocked in this environment.

## Workflow editor (`features/workflow`)

- **The chat flow is fixed** (the user asked: no more user-built graph; owners click blocks to configure them, and this may be replaced later). The backend routes each message (router → order steps / booking steps / FAQs / order status, see configuration-service's "Chat flow"); the Workflow tab shows that as a **read-only React Flow diagram** (`diagram.ts`: `flowNodes(fields, settings)` + `FLOW_EDGES`, fixed positions, nothing draggable/connectable/selectable/deletable; `steps.ts`: `FLOW_NODE_META` per block (label, description, `about`, optional `link` to a Catalog / Orders sub-tab, optional `badge`, icon, colours) and `CHAT_STEP_LABELS` for `chat_state_id`). `StepNodeView` (`components/step-node.tsx`) renders a block; handles exist only for the edges and are hidden. Clicking a block (`onNodeClick`): Details collection or Booking details (`DETAILS_NODES`: each its own list, `product_detail_fields` / `schedule_detail_fields`) opens `DetailFieldsDialog` (`kind` order / booking); any other opens `StepInfoDialog` (what it does + link). The Bookings branch (Service selection → Time slot → Booking details → Booking confirmation) links to Catalog → Services and Orders → Services.
- **API:** `GET /api/chat/configuration/` → `{id, business, product_detail_fields, schedule_detail_fields, welcome_message, reply_style, custom_style, last_updated}` for the user's business (no ID in the URL); until the business saves, the backend returns the defaults with `id` / `last_updated` null (the editor then says "Using the default settings"). `PUT` with all of them upserts; `useSaveChatConfiguration` writes the response into the query cache. Types (`types.ts`): `ChatConfiguration`, `DetailField`, `CHAT_STEPS` / `ChatStep` (mirrored from configuration-service `chat_app/constants.py`).
- **State:** the edited `fields` live in `WorkflowEditor` state (nodes in `useNodesState`, the Details block's `data.fields` synced from it). `WorkflowEditor` keeps `fields` (orders) and `bookingFields` (bookings). Dirty = either normalized list's JSON ≠ the saved one, or the settings changed. **Discard re-fetches** via the query's `refetch()` and resets from the result; it doesn't keep a local copy of the saved state (the user asked for this). Save and Discard both go through `ConfirmDialog`. `useBlocker` + `beforeunload` guard unsaved changes.
- **Unavailable routes** (the user asked: grey out what customers can't reach): `WorkflowPage` checks `useHasActiveProducts()` (`@/features/products`: reads the product pages until an active one) and `useHasBookableServices()` (`@/features/services`: an active service with an active provider, like the backend's `active_services`) and passes `unavailableRoutes` (`orders` / `bookings`) to `WorkflowBuilder` → `WorkflowEditor` (the page does it so `features/workflow` doesn't import `features/services`, which imports it). `diagram.ts`: `ROUTE_NODES`, `UNAVAILABLE_REASONS`; the route's blocks get `data.unavailable` (`StepNodeView`: dashed, faded, greyscale, with the reason) and `flowEdges()` dims and dashes the arrows into them; the info dialog says "Not in use". Unknown while loading: nothing greyed. The blocks stay clickable (Details collection's fields can still be edited).
- **Welcome & style** (the user asked: the business customises the welcome message and the reply style): a `settings` block left of the Router (edge "First message"), showing *Welcome: on / off* and *Style: …* (`data.settings`, synced from editor state). Clicking it opens `ChatSettingsDialog`: a switch + textarea for `welcome_message` (counter, *Insert {business_name}*, a preview bubble using `useCurrentUser().business_name`), the reply styles as radio cards (`useReplyStyles()`: `GET /chat/configuration/reply-styles/`, `staleTime: Infinity`), and a textarea for `custom_style` with Custom. `settings.ts` mirrors the backend limits (`SETTINGS_LIMITS`: 1000 / 500) and rules (`validateSettings`: only `{business_name}`, custom needs text), `welcomePreview`, `normalizeSettings` / `sameSettings` (trimmed, for the dirty check). Like the details, **Apply** only updates `WorkflowEditor` state (`settings`); the workflow's Save sends `{product_detail_fields, schedule_detail_fields, welcome_message, reply_style, custom_style}`, and Discard resets them from the re-fetch. The Chat Sandbox adds every message of a turn (`SandboxMessageReply.messages`: the welcome, then the reply) and shows `debug.welcome_message`.
- **Details collection fields** (the user asked for this): `ChatConfiguration.product_detail_fields` / `schedule_detail_fields: DetailField[]` (the user asked: orders and bookings collect their own; `{key, label, type: text|number|email` (no phone: customers chat on WhatsApp), description?, required? (false = optional; only `false` is stored, see `normalizeDetailField`/`withRequired`), max_length? (text), min_value?/max_value? (number)}`; the dialog has a Required switch per detail and needs at least one required) (the editor's current, maybe unsaved, copy is in `WorkflowEditor` state, passed to the node as `node.data.fields` for its chips). `details.ts` mirrors the backend rules and limits (`DETAIL_LIMITS`, keep in sync with `chat_app/validators.py`), `DEFAULT_DETAIL_FIELDS` (name + email, what the backend returns until the business saves; `detailFieldsOrDefault`) and `PRESET_DETAIL_FIELDS` (+ delivery address). Saving and the dirty check go through `normalizeDetailField` (fixed key order, type-specific keys only) so the comparison stays stable. Clicking the Details collection block opens `DetailFieldsDialog`: preset switches + editable labels, custom rows (label, type, limits, hint), client-side validation, **Apply** only updates the editor (the workflow's Save persists it). Saved keys never change (collected data is stored under them); new custom keys come from `keyFromLabel()` (preset keys are reserved). There's no frontend test runner; check pure logic with `npm run build` and, if needed, a throwaway script bundled with `node_modules/.bin/rolldown`.
- `WorkflowBuilder` shows the skeleton/error states; it only shows the error screen while there's no data at all, so a failed re-fetch never unmounts the editor and loses edits.

## Catalog → Services (`features/services`, `ServiceManager`)

- The user asked for this (businesses selling time slots, e.g. a photographer's shoots), then for service providers with week-by-week schedules. Mirrored from configuration-service `product_app` `Service` / `ServiceProvider` / `WeeklyAvailability`; three sections:
  - **Services** (`/api/services/`, CRUD like products, `?page=`): `ServiceFormDialog` (name, description, information, price, `duration_minutes` / `buffer_minutes` (multiples of 15, `SERVICE_LIMITS` in `validation.ts`), **Bookings start every** (`start_interval_minutes`: buttons for `START_INTERVAL_PRESETS` 15 / 30 / 60 or Custom (a multiple of 15, ≤ 1440), with example times from `exampleStartTimes`; the table's Starts column uses `formatStartInterval`), a checkbox per service provider (`service_providers` IDs), active). `changedServiceFields` compares the ID list order-insensitively.
  - **Service providers** (`/api/service-providers/`, first page only: 20): a card each (name, note, inactive badge, its services, **View schedule**); `ProviderFormDialog` (name, description, active), `DeleteProviderDialog`.
  - **Schedules** (`ProviderSchedule`, URL `?provider=` (default the first) and `?week=` (any day, read as its Monday; this week is left out)): `GET /service-providers/{id}/calendar/?week=` (`WeekCalendar`: letters, `time_zone`, `id` (null: no row yet, all U) and `bookings` with who booked, status and `start_block` / `end_block` / `until_block`, their positions in the letters). `ScheduleGrid` (days across, 96 rows of `ROW_HEIGHT` px, every element placed explicitly in the CSS grid so bookings are drawn over their duration as buttons; buffer cells open their booking via `bookingAt()`) → `BookingBlockDialog` (customer, service, times in the schedule's time zone, status badge (`OrderStatusBadge` from `@/features/orders`), details with `useDetailLabels()`, links to `/orders/services?booking=N` and the chat). **Edit hours**: a draft painted with an O / U brush (booked H / X blocks can't be painted, as the backend refuses them), saved with `saveWeek()` (POST `/weekly-availabilities/` when `id` is null, else PATCH) after `applyEdits()` puts the changed blocks onto the latest letters (a booking made meanwhile is kept); week / provider navigation is disabled while editing. **Add slots** (`AddSlotsDialog`: dates, weekdays, times (`24:00` allowed), open / close → `POST …/{id}/slots/`, `validateSlots()`), **Copy previous week** (`POST …/{id}/copy-week/` with `source_week` = last week, `target_week` = this one) and **Copy to next weeks** (`CopyWeekDialog`, 1–`WEEKS_CHANGED_MAX` weeks); results are summarised with `describeChange()` (`schedule.ts`).
- `availability.ts` mirrors the backend letters (672, block 0 = Monday 00:00, local time of `DJANGO_SCHEDULE_TIME_ZONE`; `SLOT_META` O available / U unavailable / H on hold / X booked; `EDITABLE_LETTERS` O, U; `paint()` skips booked blocks) and has the YYYY-MM-DD date helpers (`mondayOf`, `addDays`, `formatWeek`…). The grid shows times as they are in that zone. Saves / deletes / slot changes go through `ConfirmDialog`. Keys: `serviceKeys`, `providerKeys` (`list`, `calendar(id, week)`); service and provider mutations invalidate both, schedule changes `providerKeys.calendars()`.

## Chats tab (`pages/chats-page.tsx`)

- Sub-tabs (routes): **Conversations** `/chats/conversations` (`ChatSessionBrowser`, below), **Unanswered questions** `/chats/questions` (`QuestionsBrowser`, `features/questions`) and **Chat Sandbox** `/chats/sandbox` (below). Each has its own URL and filters. The questions tab shows a red count badge, and Conversations an `OpenQuestionsAlert` banner, while any questions are open: `useOpenQuestionCount()` (`GET /chat/questions/?status=open&page_size=1` → `count`, polled every 60 s).
- **Unanswered questions** (`features/questions`, mirrored from configuration-service `chat_app` `UnansweredQuestion`): questions the assistant couldn't answer (saved by the backend's question check, which runs when its router finds a question). `GET /chat/questions/` (`status`, `page`, `page_size`; `?status=` in the URL, `open` default, or `all`), `POST /chat/questions/{id}/answer/` `{answer, question?}` (saves an FAQ and sends `answerMessage()` = `Regarding your previous question about "<question>": <answer>` in the chat), `POST /chat/questions/{id}/dismiss/`. `AnswerQuestionDialog` (editable question wording, answer with counter, a preview of the chat message; `QUESTION_LIMITS` mirror the backend) and Dismiss both go through `ConfirmDialog`. ## Conversations (`features/chat-sessions`, `ChatSessionBrowser`)

- **Read only** (the user asked): no edit/delete here. `GET /chat/sessions/` → `DetailedPaginated<ChatSession>` (`@/types/api`: adds `total_pages`, `current_page`, `page_size`, `has_next`, `has_previous`). Query params follow the backend `ChatSessionFilter`: `sandbox` (`exclude` default / `include` / `only`), `search`, `chat_state_id`, `has_messages`, `last_chat_time_after|before`, `created_time_after|before`, `ordering`, `page`, `page_size` (10/20/50/100).
- **State lives in the URL** (`useChatSessionParams`): short names `search`, `state`, `messages`, `sandbox`, `last_from`/`last_to`/`created_from`/`created_to` (YYYY-MM-DD, sent as local start/end-of-day ISO via `toListParams`), `ordering`, `page`, `page_size`, and `chat` (open conversation). Defaults are omitted from the URL; invalid values fall back to defaults; changing any filter resets `page`. Search is debounced in the input's change handler (300 ms).
- `useChatSessions(params)` (`keepPreviousData`, key `chatSessionKeys.list(params)`). Step names come from `useChatSteps()` (the fixed steps: `@/features/workflow` `CHAT_STEPS` + `CHAT_STEP_LABELS`; also the "Current step" filter options). The conversation dialog uses `ChatMessageBubble perspective="business"` and shows `ChatStateSummary`. Errors: 403 no business, 404 page past the end ("Go to the first page"), 400 invalid URL filters ("Clear filters").
- `components/ui/native-select.tsx` is a hand-written styled native `<select>`.

## Chat Sandbox (`features/chat-sessions`)

- **Sandbox sessions only** (`is_sandbox`), all login-required and scoped to the user's business by the backend: `GET /chat/sandbox-sessions/?page=` (list), `POST /chat/sandbox-sessions/` `{display_name?, phone_number?}` (create; no saved chat configuration needed), `DELETE /chat/sandbox-sessions/{id}/`, `POST /chat/sandbox-sessions/{id}/messages/` `{message}` → reply `ChatMessage`. (The public `/chat/sessions/messages/` is for the future webhook; don't use it here.)
- **UI:** `ChatSandbox` → list (`SandboxSessionList`) + `SandboxChatWindow` (keyed by session id). The selected chat is `?session=<id>` (falls back to the most recent chat if missing/deleted). New chats are named `nextSandboxChatName()` ("Test chat N"). Drafts are kept per chat in the parent. Delete goes through `ConfirmDialog`.
- **Data:** `useSandboxSessions()` is a `useInfiniteQuery` (key `chatSessionKeys.sandboxList()`); messages come from the list data (there's no session-detail API). `useSendSandboxMessage(id)` has `mutationKey` `chatSessionKeys.sendSandboxMessage(id)`: it appends the customer message optimistically, appends the reply on success and invalidates the list on settle. Its callbacks live on the mutation, so they still run if the user switches chats; `useIsSendingSandboxMessage(id)` (`useIsMutating`) drives per-chat typing indicators across remounts.
- The send request overrides the client timeout (`SEND_MESSAGE_TIMEOUT_MS = 300_000`): a message makes several Ollama calls on the backend (the chat flow: the router, one extraction per order step passed, maybe the question check, plus the reply), each allowed up to 120 s.
- **Chat flow state:** `ChatSession.chat_state_data` (`ChatStateData` in `types.ts`, mirrored from configuration-service `validate_chat_state_data`: optional `items` `[{product_id, name, unit_price (decimal string), quantity}]`, `items_confirmed`, `details` `Record<field key, string | number>`, `last_order_id` (the last order placed; the chat is then back at `start`), and for bookings `service`, `slot`, `slot_options`, `last_booking_id`) is read only here. `SandboxChatWindow` shows a strip under the header: the step (`useChatSteps().stepLabel(chat_state_id)`) + `ChatStateSummary` (`components/chat-state-summary.tsx`: order with a cents-based total, each detail labelled via `useDetailLabels(kind)` (`order`: `product_detail_fields`, `booking`: `schedule_detail_fields`, or the defaults; falls back to the key), and an *Order #N placed* badge linking to it; for a booking, the service, price and chosen time (or how many times are offered), and a *Booking #N made* badge → `/orders/services?booking=N`). It refreshes through the list re-fetch after each send (the optimistic update only adds messages).
- **Debug panel** (`SandboxDebugPanel`, open while `?debug` is in the URL; toggled by the bug button in `SandboxChatWindow`'s header, rendered by `ChatSandbox` beside the window): saved state (raw `chat_state_id`, its step label, and `chat_state_data` as JSON) and the latest turn: state before → after, **Router** (`debug.route`: intents with labels, its prompt and JSON), **Order steps** (`FlowStepDebug` per step: `step`, the LLM's JSON, complete / not complete / "Went back to <step>", missing, issues, prompt), **Question check** (`debug.question_check`: kind none / answered / unanswered, the question, whether it was saved; null → "Not run"), and the reply (still needed, issues, tool calls, the reply prompt; `debug.confirmation`: Confirmation's substage (`not_confirmed` / `confirmed`); **Order status** (`debug.order_status`, `OrderStatusDebug`, shown when the router found an order status request: the extraction's JSON, what was found / not found, the records given to the reply, the extraction prompt); `debug.reply_kind`: `llm`, `order_status` (written by the LLM from the records only), `order_status_fallback` / `order_status_not_found` (written by code) or a fixed template (`confirmation_request`, `order_confirmed`, `slot_options`, `booking_confirmation_request`, `booking_confirmed`), whose `reply_system_prompt` is the LLM aside's, or empty). The send response is `SandboxMessageReply` (`ChatMessage` + `debug: SandboxTurnDebug`); `useSendSandboxMessage` strips `debug` before adding the message to the list cache and puts it under `chatSessionKeys.sandboxTurnDebug(id)` (`gcTime: Infinity`, never fetched: `useSandboxTurnDebug` is a disabled query). So the latest turn is lost on reload, by design; the backend doesn't store it.

## WhatsApp card (`features/whatsapp`, `WhatsAppSettingsCard` on Home)

- **API** (configuration-service, the user's own business, no ID in the URL): `GET /configuration/whatsapp/` → `WhatsAppConfiguration` `{phone_number_id, display_phone_number, verified_name, webhook_url, verify_token, created_time, last_updated}` (`display_phone_number` / `verified_name` come from Meta, read only; shown by `ConnectedNumber`); `getWhatsAppConfiguration()` turns a 404 into `null` (not connected). `PUT` with `{phone_number_id, access_token?, app_secret?}` connects (201) or updates (200); `DELETE` disconnects. **The secrets are write-only**: never returned, so the form only holds a secret the owner is typing; empty secrets are left out of the PUT (`formValuesToWhatsAppInput`), which keeps the saved ones. Both are required when connecting. The user asked to keep only these three fields (no display phone number / WABA ID / App ID) and no `has_*` flags (a connection always has both secrets).
- **Hooks:** `whatsAppKeys`, `useWhatsAppConfiguration(enabled)` (enabled only when logged in), `useSaveWhatsAppConfiguration` / `useDeleteWhatsAppConfiguration` write the result (or `null`) into the cache.
- **UI:** the card handles its own auth (it's on Home, which isn't behind `RequireAuth`; `RequireAuth` would render a whole-page "Log in required" and change the tab title): logged out → `LoginDialog`; 403 → "not linked to a business". Connected → a "Webhook setup in Meta" panel (Callback URL + Verify token, `CopyField` with `navigator.clipboard`, plus the 3 Meta steps) above the form. One form for both states, remounted with `key={config.last_updated}` after each save. **Connected = locked** (the user asked): the inputs are disabled with **Edit** + Disconnect; Edit unlocks the Phone Number ID and shows **Save changes** + **Cancel** (Disconnect hidden; Cancel resets everything and locks again). **Saved secrets: masked + Replace** (the user chose this over "leave blank to keep"): `SavedSecret` shows a disabled input with dots (display only, never a form value; "saved and hidden" via `aria-describedby`), with a **Replace** button while editing; Replace (`replacing[field]`) swaps in an empty, focused password input + **Keep current** (clears the typed value); a Replace left empty is a validation error ("Enter the new …, or click Keep current.", `validateWhatsApp(values, isConnected, replacing)`), never a silent keep; a successful save remounts the form, so it's locked again; on an error it stays in edit mode. Not connected = always editable. **Connect** disabled until all three fields are filled (non-blank; the user asked, since all are required); **Save changes** disabled until something changes (`changedWhatsAppFields`). Format errors (digits only, no spaces) show on click. Connect, Save and Disconnect all go through `ConfirmDialog`; the backend checks every save with Meta, so Connect/Save show the pending label "Checking with Meta…", Meta's rejections arrive as 400 field errors (shown by `getFormErrors`) and an unreachable Meta as a 503 form error. Limits/rules in `validation.ts` (`WHATSAPP_LIMITS`, digits-only Phone Number ID ≤ 32, secrets no spaces, ≤ 1000 / ≤ 128), mirrored from configuration-service `configuration_app/models.py`.

## Authentication (JWT from configuration-service)

- **Backend endpoints:**
  - `POST /api/auth/token/`: `{username, password}` → `{access, refresh}`.
  - `POST /api/auth/token/refresh/`: `{refresh}` → `{access, refresh}`. Refresh tokens **rotate**, and the old one is blacklisted.
  - `POST /api/auth/logout/`: `{refresh}` blacklists it.
  - `GET /api/auth/me/` → `CurrentUser` (`id`, `username`, `email`, names, `business` id | null, `business_name`, `is_staff`, `is_superuser`).
  - Lifetimes: access 15 minutes, refresh 7 days.
- **Tokens** live in `useAuthStore` (`src/stores/auth-store.ts`, Zustand `persist` → localStorage key `auth`). A `storage` event listener rehydrates it, so tabs stay in sync. "Logged in" means a refresh token is present (`selectIsAuthenticated`).
- **`createApiClient` handles auth for every request, so never add auth headers or refresh logic in feature code:**
  - The request interceptor adds `Authorization: Bearer <access>`.
  - On a 401, the response interceptor calls `refreshAccessToken()`, which is single-flight via a shared promise. It uses bare `axios`, so it bypasses the interceptors. It then retries the request once (`_retriedAfterRefresh`).
  - If the refresh fails, it calls `clearTokens()` and rejects with the original 401.
  - Pass `{ skipAuth: true }` for requests that must not carry or refresh tokens (login/logout).
  - The `skipAuth` and `_retriedAfterRefresh` config fields are declared by module augmentation in `api-client.ts`.
- **Component API:** `useAuth()` from `@/features/auth` returns `{ isAuthenticated, user, isLoadingUser, login, isLoggingIn, loginError, resetLoginError, logout }`. `useCurrentUser()` is the `/me` query (key `authKeys.currentUser`).
- **Cache safety:** `useResetQueriesOnAuthChange()` (mounted in `AppProviders` via `GlobalEffects`) resets all queries on any login or logout, including an expired session or another tab. It excludes the current-user query, because `login()` fetches that itself and resetting would cancel it. On logout, the current-user query is removed. Keep this behaviour when changing auth.
- **Retries:** `queryClient` doesn't retry 4xx errors (`shouldRetry`), so a 401 or 403 isn't retried pointlessly.
- **Login guard: `RequireAuth`** (`features/auth/components/require-auth.tsx`, exported from `@/features/auth`).
  - It renders `children`, or `<Outlet />` when used as a layout route, when `selectIsAuthenticated` is true. Otherwise it shows a "Log in required" card with a `LoginDialog`.
  - It doesn't redirect: after login the page renders in place, and after logout the message replaces it.
  - **Protect pages by adding them to the pathless `{ element: <RequireAuth />, children: [...] }` group in `src/app/routes.tsx`**, currently Workflow, Product, Service, Orders, FAQ, Chats and Chat Sandbox. Don't add auth checks inside page components.
  - It's UI only; the backend still enforces 401/403.
- **Not built yet:** an "expired session" toast, and role-based UI.

## Environment notes for Claude

- The shadcn CLI needs `ui.shadcn.com`, which the Apple Claude Code sandbox blocks by default, so `npx shadcn add` fails until the user allows that domain. If it's blocked, write the component source by hand into `src/components/ui/`, following the existing files.
- The sandbox also blocks listening on local ports, so `npm run dev` / `preview` can't be smoke-tested from inside Claude. Use `npm run build` to verify.
