# CLAUDE.md: configuration-service

Guidance for Claude Code when working in `configuration-service/`.

## What this is

A Django REST API backend for Ansera Business Admin. It is consumed by `../frontend-app` (the Vite dev server runs at `http://localhost:5173`).

## Stack (keep to these; don't swap libraries without asking)

- **Django 6.1** (Python 3.12+). Project package: `config/`. Settings are in `config/settings.py`.
- **Django REST Framework** for all API endpoints: serializers + `APIView`/viewsets. Don't write plain Django `JsonResponse` views.
- **drf-spectacular** for OpenAPI 3 / Swagger docs. `DEFAULT_SCHEMA_CLASS` is set in `REST_FRAMEWORK`. The docs are at `/api/docs/` (Swagger UI) and `/api/redoc/`, and the schema is at `/api/schema/`. Use `@extend_schema` where auto-generated docs are unclear.
- **django-filter** (`django_filters` in `INSTALLED_APPS`) for list filtering/sorting: a `FilterSet` per list (e.g. `chat_app/filters.py` `ChatSessionFilter`), set with `filter_backends = [DjangoFilterBackend]` + `filterset_class` on the view (not globally). drf-spectacular documents the parameters automatically. Use `StableOrderingFilter`-style ordering (append `-id`) so pages stay stable. Prefer `ChoiceFilter` over `BooleanFilter` (which ignores invalid values instead of returning 400).
- **Pagination for rich lists:** `config.pagination.DetailedPageNumberPagination` (`page`, `page_size` ≤ 100; response adds `total_pages`, `current_page`, `page_size`, `has_next`, `has_previous`). Set it per view with `pagination_class`; the global default is still DRF's `PageNumberPagination`.
- **django-cors-headers**. `CorsMiddleware` must stay the **first** entry in `MIDDLEWARE`, above `SecurityMiddleware`, so that responses generated by other middleware still get CORS headers. `CORS_URLS_REGEX` limits CORS to `/api/`. Allowed origins come from `DJANGO_CORS_ALLOWED_ORIGINS` (default: the Vite dev server). Never use `CORS_ALLOW_ALL_ORIGINS = True`.
- **Database:** SQLite (`db.sqlite3`, git-ignored, disposable) by default when run directly; **PostgreSQL** (`psycopg` 3) when `DJANGO_DB_ENGINE=postgresql`, configured by `POSTGRES_DB/USER/PASSWORD/HOST/PORT` (`config/settings.py`; any other value raises `ImproperlyConfigured`). Keep the code database-agnostic (no raw SQLite- or Postgres-specific SQL); `select_for_update` really locks only on PostgreSQL.
- **Docker** (the user asked): `Dockerfile` (python:3.14-slim, dev server) + `docker-entrypoint.sh`, which runs `migrate`, then: with `RESET_DB=true`, `flush` + `loaddata` of all 10 fixtures + creates `superuser` / `123`; otherwise (the default, the user asked: data must survive restarts) keeps the data, loading the fixtures and superuser only when the database is empty (no BusinessConfiguration); then `exec "$@"` (default `runserver 0.0.0.0:8000`). The root `docker-compose.yml` runs it (`RESET_DB: ${RESET_DB:-false}`) with `postgres:17-alpine` (named volume `postgres-data`, host port 5433, healthcheck; the app waits for it), `DJANGO_DB_ENGINE=postgresql` and `OLLAMA_HOST=${OLLAMA_HOST:-http://host.docker.internal:11434}` (Ollama stays on the host: the user removed an `ollama` container, since the Docker VM has too little memory for the model; the host's Ollama must listen on 0.0.0.0, and a vessel VM needs `OLLAMA_HOST=http://192.168.64.1:11434` in the root `.env`; see the root README, "Local LLM"). When adding a fixture, add it to the entrypoint's `loaddata` too. The Docker daemon isn't reachable from Claude's sandbox: validate with `docker compose config` and let the user run it.

## The database schema is owned here (the user's rule)

- **All PostgreSQL migrations are done here, and only here.** Every schema change (tables, columns, indexes, constraints, data migrations) is a Django model change plus a migration (`makemigrations`, committed). No other service runs migrations or DDL.
- Other services connect only to query the data (and write rows where their job needs it):
  - messaging-service's chat flow: chat messages and state, orders, bookings, questions;
  - processing-service: payment status and booking weeks;
  - notification-job: reads only.

  They map the tables with SQLAlchemy. **When changing a model those services use, update their mappings too** (`messaging-service/app/models.py`, `processing-service/app/models.py`, `notification-job/app/models.py`). CI's `schema` job migrates PostgreSQL with these migrations and checks the messaging-service and processing-service models against it.
- Model defaults (e.g. `new_payment_reference`, `auto_now`) and signals (e.g. `checkout_app.signals` painting bookings into weeks) don't run in those services. A new default or side effect that another service's writes must respect needs porting there too.
- **The chat flow is also in messaging-service** (`messaging-service/app/chat_flow`, a SQLAlchemy port of `chat_app`'s `flow`, `order_flow`, `router`, `prompts`, `tools`, `past_orders`, `ask_business`, plus `checkout_app`'s `place_order` / `place_booking` / schedule / stock). The frontend's Chat Sandbox sends messages there now. This service keeps `CustomerMessageView` / `SandboxChatMessageView` and `POST /api/chat/` for now (the user asked not to remove them yet), so **change both copies together** (and the ported tests, `messaging-service/tests/test_chat_*.py`) until they're removed here. Logins: messaging-service checks this service's access tokens with the same `JWT_SIGNING_KEY` (`SIMPLE_JWT['SIGNING_KEY']`, default `SECRET_KEY`).

### Chat flow (`chat_app/flow.py`, `router.py`, `order_flow.py`, `prompts.py`, `tools.py`)

The user asked for a **router + sub-flows** design (replacing the user-built block graph): the flow is fixed in code, each business only configures its steps (`ChatConfiguration`), and each sub-flow is a small deterministic state machine. Per customer message, `flow.handle_customer_message()`:
1. Saves the message (`append_chat_message`).
2. **Routes** (`router.route_message`): one `llm.generate_structured` call (`prompts.ROUTER_SCHEMA` `{intents: [..]}`, temperature 0) with `build_router_prompt()` (business name + description, product names, where the order is: none / in progress at step X / already placed #N). `intents` ⊆ `constants.INTENTS`: `order`, `booking`, `question`, `order_status` (past orders or bookings), `off_topic` (several allowed; empty for greetings/thanks); `router.clean_intents()` keeps known ones, once, in `INTENTS` order. `Route` exposes `start_order`, `question`, `order_status`, `off_topic`, `only_order_status`. **Code, not the model, picks the handlers.**
3. **Order sub-flow** (`order_flow.advance(chat_config, step, data, history, products, start_order=)`): Product selection → Details collection → Confirmation (`ORDER_STEPS`, `NEXT_STEP`). At `start` nothing runs unless `start_order` (then Product selection runs on the same message). **While an order is in progress, its steps run on every message whatever the router says** (short replies like "Alice" carry no intent). After the order is placed (`completed`), no extraction. Unknown steps fall back to `start`.
   - **Extract** with `llm.generate_structured(system_prompt, history, schema)`: Ollama `format=<JSON schema>`, `STRUCTURED_OPTIONS` (temperature 0); invalid JSON → `LLMError` (502). Schemas come from `prompts.extraction_schema(step, fields, go_back)` (static `EXTRACTION_SCHEMAS`, except the details steps, built from the branch's detail fields), task prompts from `_EXTRACTION_TASKS`: Product selection `{items: [{product_id, quantity|null}], done_choosing}`, Details collection one nullable key per field (`number` fields typed as numbers), Confirmation `{decision: confirm|change|none}`.
   - **Check deterministically** with `order_flow.CHECKS[step](extracted, data, products, fields) → CheckResult(complete, missing, issues, go_back)`, updating `chat_state_data` in place. Never trust the LLM's values: products must be the business's active ones (`tools.active_products`) with 1 ≤ quantity ≤ `quantity_available` (`order_flow.item_problem()`: sold out (0 available) comes first, "has run out"); the cart kept from earlier messages is re-checked against current stock on every message, and items that can't be ordered any more are dropped (with an issue, so `items_confirmed` is cleared) (the user asked); Product selection then waits for the customer to confirm the cart (the user asked: recap, "anything else?", only then details): it completes only if `done_choosing` is true **and** the cart (`_cart()`: (product_id, quantity) pairs) didn't change in that message, or `items_confirmed` is already set; a changed cart clears `items_confirmed`; details go through `order_flow.clean_detail_value()` by type (text `max_length`, number parse + bounds, `EmailValidator`; no phone type: customers chat on WhatsApp, so the chat has their number); known details are kept when the LLM returns null; ints exclude bools. Complete → the next step, and the loop runs again there (bounded by `MAX_STEPS_PER_MESSAGE`), so one message can pass several steps. `change` at Confirmation → back to Product selection (data kept, so complete steps pass straight through). A Confirmation reached in the same message is not extracted (the customer hasn't seen the summary). **Confirmation substages** (the user asked, after the LLM told a customer "your order is confirmed" before anything was saved): `not_confirmed` (the chat sends the summary, a fixed template, and waits; anything but a clear "confirm" (`_EXTRACTION_TASKS[confirmation]` is strict: "no, nothing else" is `none`) re-sends it) → `confirmed` (the order is saved in `commit_turn()`, **then** the fixed confirmation message is sent; the chat goes straight back to `start` with `chat_state_data = {last_order_id}`, so the customer can order again). `confirmed` only exists within that turn (`Turn.confirmation_status`, `debug.confirmation`); a saved chat at `confirmation` is always `not_confirmed`. After an order, `start` + `last_order_id` (the router and reply prompts mention it); a new order starts from scratch.
   - **Going back** (the user asked: back to a specific earlier step, without losing data): `order_flow.GO_BACK_TARGETS` (Details collection → `product_selection`; Confirmation → `product_selection`, `details_collection`); `extraction_schema(..., go_back)` adds a required `go_back_to` (enum | null) and `build_extraction_prompt(go_back=)` a "Going back" section. A valid `go_back_to` (before the step's check) moves there, keeps `turn.data` (except: target Product selection drops `items_confirmed`), records a step with `go_back_to`, sets `Turn.went_back_to`, and continues there on the same message. Only offered at the step the chat was at when the message arrived (`entered_now` false): a step reached during the turn gets none, because the message that completed the earlier step would read as "go back" (a real bug). So at most one go-back per turn. The reply prompt gets `went_back=True` when the turn ended on that target.
4. `order_flow.commit_turn()` writes `chat_state_id` / `chat_state_data` (validated) and fills an empty `display_name` from `details.name`. Saved before the reply, so it's kept if only the reply fails.
5. **FAQ handler** (`check_customer_question`, below), only if the router found a `question`.
6. **Reply.** **At Confirmation the reply is always a fixed template** (the LLM must never decide what's confirmed): `prompts.confirmation_request_message(data, labels)` (summary: items, total, details, then "Please reply CONFIRM…") while `not_confirmed`, or `prompts.order_confirmed_message(business, order_id, data, labels)` once the order is saved. If the message also has a question (answered / unanswered), an order status request or an off-topic part, `prompts.build_aside_prompt()` (the intro rules + "the summary / confirmation is sent automatically: don't summarise or say anything about it being confirmed", no order data) gets a short LLM aside, put before the summary request or after the confirmation. `debug.reply_kind`: `llm` / `order_status` / `order_status_fallback` / `order_status_not_found` / `confirmation_request` / `order_confirmed` / `slot_options` / `booking_confirmation_request` / `booking_confirmed`. **Order status branch** (the user asked: customers check their own past orders and bookings; first built with tools, then, after a small model made up bookings when a tool said "not found", the user asked for this): **no tools, no states**. Whenever the router finds `order_status`, `flow.check_order_status()`: 1. one `llm.generate_structured` call (`prompts.ORDER_STATUS_SCHEMA` `{kind: order|booking|any, numbers: [int]}`, `build_order_status_extraction_prompt`: "never make up a number"), made safe by `past_orders.clean_request()` (unknown kind → any; positive ints, "#12" ok, once, ≤ `NUMBERS_MAX` 5); 2. `past_orders.lookup(session, kind, numbers, now)`, plain code, **only among the customer's own** (`customer_sessions(session)`: same business, same phone number, real or sandbox like the chat; sandbox chats without a phone number are one test customer, so a test order can be checked from another test chat (the user asked)): numbers → their orders / bookings with that number (both tables if `any`; the other kind too if not of the kind asked: customers mix the words up), else "not found" (`Lookup.not_found`, the same whether or not someone else has it); no numbers → their orders / bookings newest first (≤ `LIST_MAX` 10); records (`order_record` / `booking_record`) with `status` (Payment pending / Payment received / Completed) and `status_meaning`; 3. `prompts.format_order_records(found)` = the only facts. Reply: a message only about this, with no order step run: nothing of theirs found → `prompts.order_status_fallback_message(found)` (code, no LLM call, `reply_kind` `order_status_not_found`); else `prompts.build_order_status_prompt(business, records)` (strict rules: only what the records say, copy numbers / dates / prices / statuses exactly, "not found" → couldn't find it, never that it's someone else's, no answer → say you don't know and the team can help, no payments / changes / cancellations) with **no tools** (`reply_kind` `order_status`), then `past_orders.reply_is_grounded(reply, found)` (every `#N` / "order N" mentioned must be found or asked about, and a sentence naming a not-found number must say it wasn't found) or the fallback message is sent instead (`order_status_fallback`). With other intents, `prompts.order_status_section(records)` goes into the reply / aside prompt (`order_records=`; not grounding-checked). `debug.order_status` = `{extracted, system_prompt, records, found}` (null when not asked). Tests: `tests/test_past_orders.py` (scope, lookup, clean_request, grounding, the records text and fallback, no order tools) and `RouterFlowTests` in `tests/test_flow.py` (the fake LLM answers the extraction via `order_status=`; `is_order_status_check`). Otherwise `llm.generate_chat_reply(system_prompt, history, toolbox)` with `prompts.build_reply_prompt(business, step, data, products=, fields=, missing=, issues=, finished=, went_back=, intents=, question_check=)`: business info, step + goal (`STEP_GOALS`; `start` = no order in progress), collected data with a Python-computed total, details to collect, still-needed list, issues, catalog for `start` / Product selection, the question section, an order status section (`order_status` intent: `order_status_section(records)`, the customer's records looked up) and an off-topic section (`off_topic` intent: decline that part politely), then per-step `_REPLY_INSTRUCTIONS` (not Confirmation: templates). The intro says never to tell the customer an order is confirmed or placed (the system does that once it's saved). Up to `MAX_TOOL_ROUNDS` of tool calls; `tools.Toolbox` holds **read-only, business-bound** tools, each `name → (description, JSON-schema parameters, function(arguments))`: `get_product_details(product)` (the user asked: one product's `description` + `information` by name/id via `find_product_details()`; errors list matches or what's on sale), `list_products` (`tools.active_products()`: descriptions, never `information`), `list_faqs`. The catalog in prompts shows each (short) description in full, on one line; `information` only ever comes from `get_product_details` or the question check (the user asked: description = what the assistant tells customers the product is; information = long extra context, looked up only when a question needs it). The reply prompt tells the model to answer "what is it" from the description, other product questions via `get_product_details` (answer the question, don't recite the information), business questions via `list_faqs`, and to **say it doesn't know instead of making things up** (the user asked). ### APIs and access control

- **Endpoints:** `product_app` has CRUD `ModelViewSet`s for `/api/products/`, `/api/faqs/`, `/api/service-providers/`, `/api/weekly-availabilities/` and `/api/services/`, registered with a `DefaultRouter` in `product_app/urls.py` and mounted at `/api/` in `config/urls.py`. `auth_app` has the auth endpoints under `/api/auth/` (`auth_app/urls.py`): `token/` (login), `token/refresh/`, `token/verify/`, `logout/` (blacklists the refresh token), and `me/` (`MeSerializer`: profile + `business` ID + `business_name`, read-only). The token views are thin subclasses of SimpleJWT's views (`LoginView`, `RefreshView`, `VerifyView`, `LogoutView`) that add Swagger docs under the `Auth` tag. `product_app` also has read-only `BusinessProductListView` / `BusinessFAQListView` at `/api/businesses/<int:business_id>/products/` and `/faqs/` (URL names `product_app:business-product-list` / `business-faq-list`). They list **all** of that business's records, including inactive products, and are paginated. There are no business-configuration or user-management APIs yet.
- **Business scoping (`auth_app/business_scope.py`):** reuse this for every business-owned model.
  - `IsBusinessMember`: object-level `obj.business_id == user.business_id`, so another business's record returns **403, not 404** (the user asked for 403). Users with no business get 403 on every unsafe method.
  - `BusinessScopedViewSetMixin`: the `list` action is filtered to the user's business; detail routes use the unfiltered queryset so the permission can return 403.
  - `BusinessFromUrlMixin`: for views with a `business_id` URL kwarg. It runs in `initial()`, after auth, so **401 comes first**. Then:
    - An unknown ID raises `ValidationError` → **400**. The user explicitly asked for 400 rather than 404.
    - Another business, or a user with no business, gets **403**.
    - Otherwise it sets `self.business`.

    Its `get_queryset()` must return `.none()` when `swagger_fake_view` is set (schema generation).
  - `BusinessOwnedSerializerMixin`: a `business` field that defaults to the user's business (`CurrentUserBusinessDefault`). Any other business raises `PermissionDenied` (403) in `validate_business`. Because it has a default, DRF's `UniqueTogetherValidator` still works for the per-business unique constraints.
- **The derived quantities (`quantity_available`, `quantity_on_hold`, `quantity_sold`) are read-only in the API** (`DERIVED_QUANTITY_FIELDS`). `ProductSerializer.to_internal_value` explicitly returns 400 (`DERIVED_QUANTITY_ERROR`) when one is sent, reported together with other field errors, instead of DRF's default of silently ignoring it. Only `total_quantity` is writable (see `product_app` above).
- **DRF defaults (`REST_FRAMEWORK`):**
  - `DEFAULT_PERMISSION_CLASSES = IsAuthenticated`, so endpoints are private by default. Public endpoints must opt out: `RandomNumberView` sets `permission_classes = [AllowAny]` and `authentication_classes = []`.
  - `PageNumberPagination`, `PAGE_SIZE = 20`. List responses are `{count, next, previous, results}`.
  - Authentication, in order:
    1. **`JWTAuthentication`** (SimpleJWT, `Authorization: Bearer`). This is what `frontend-app` uses. Being first means unauthenticated requests get 401 with `WWW-Authenticate: Bearer`.
    2. `BasicAuthentication`, **only when `DEBUG`**, for Swagger's Authorize dialog.
    3. `SessionAuthentication`. drf-spectacular's Swagger UI sends the CSRF token, so it works there too.
  - **`SIMPLE_JWT`:** access 15 minutes, refresh 7 days, `ROTATE_REFRESH_TOKENS` + `BLACKLIST_AFTER_ROTATION` (needs the `rest_framework_simplejwt.token_blacklist` app, which is installed and migrated), `UPDATE_LAST_LOGIN`.
  - drf-spectacular's built-in SimpleJWT extension adds the `jwtAuth` security scheme to Swagger.
  - The frontend stores tokens in localStorage and refreshes them on 401 (see `../frontend-app/CLAUDE.md`).
- **Swagger docs:** keep the `@extend_schema_view` docs (tags `Products` / `FAQs`, summaries, 403 responses) up to date for new actions. Decimal fields are strings in the schema, so document numeric limits in `help_text`.

### Model conventions

- **Length limits are module-level constants** in each `models.py` (e.g. `PRODUCT_NAME_MAX_LENGTH`), reused in tests. Current limits:
  - Names: 150 characters.
  - Locations: 255 characters.
  - FAQ questions: 300 characters.
  - Descriptions: 2,000 (business) and 300 (product) characters. Product information: 5,000 characters.
  - FAQ answers: 10,000 characters.
- **`TextField(max_length=...)` isn't enforced by Django at the model level.** Always add `validators=[MaxLengthValidator(N)]` alongside it, as the existing models do.
- **Validation lives in both Django and the database.**
  - Field validators (`MinValueValidator`, `PositiveIntegerField`) catch bad values in forms, admin and serializers.
  - `Meta.constraints` catch them at the database level: `CheckConstraint` for non-negative prices and non-empty strings, `UniqueConstraint` for product name and FAQ question per business.
  - Django 6 uses `CheckConstraint(condition=...)`; the old `check=` argument was removed.
- **Quantity cap:** quantities are capped at `QUANTITY_MAX = 1_000_000` with a `MaxValueValidator`.
- **Primary keys:** `BigAutoField` (Django 6 default).
- **Admin:** register every model with `list_display`, `search_fields`, `list_filter` and `list_select_related`. Use `autocomplete_fields` for the `business` FK, which works because `BusinessConfigurationAdmin` has `search_fields`.
- **Serializers:** when you add them, reuse the model validators. DRF `ModelSerializer` picks them up automatically, and `UniqueConstraint` becomes a `UniqueTogetherValidator`.

### General

- All API routes live under `/api/`.
- Settings read from environment variables (`DJANGO_DEBUG`, `DJANGO_SECRET_KEY`, `JWT_SIGNING_KEY`, `DJANGO_ALLOWED_HOSTS`, `DJANGO_CORS_ALLOWED_ORIGINS`, `DJANGO_SCHEDULE_TIME_ZONE`, `CONFIGURATION_ENCRYPTION_KEY`, `INTERNAL_API_KEY`, `MESSAGING_INGESTER_PUBLIC_URL`, `META_GRAPH_API_URL`) with local-dev defaults. When adding a new setting, add it to `.env.example` and the README table.
- The host Python is 3.8 (too old for Django 6.1) and there's no `.venv`: run commands in the Docker image with the source mounted, as your user (or created files end up owned by root), e.g. `docker compose run --rm --user "$(id -u):$(id -g)" --entrypoint python -v "$PWD/configuration-service:/app" configuration-service manage.py test` from the repo root. Rebuild the image after changing `requirements.txt`. The Docker daemon is reachable.
- Add new dependencies to `requirements.txt` with a version range.
- After changing models, run `makemigrations` and commit the migration files. Don't edit applied migrations; the database is still disposable, but teammates may have it. This is the only place migrations happen (see "The database schema is owned here" above).

- **Test layout:** each app's tests are `tests.py` / `test_api.py`, except `chat_app` and `checkout_app`, which have a `tests/` package (`chat_app`: `test_models.py`, `test_api.py`, `test_flow.py`, `test_booking_flow.py`, `test_tools.py`, `test_questions.py`; `checkout_app`: `test_models.py`, `test_services.py`, `test_stock.py`, `test_schedule.py`, `test_api.py`; the user asked, to keep app folders tidy). Run one with e.g. `python manage.py test chat_app.tests.test_flow`.

## Commands (run from `configuration-service/`, with `.venv` active or via `.venv/bin/python`)

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py loaddata sample_business_configurations sample_business_users sample_products sample_faqs sample_services sample_chat_configurations sample_chat_sessions sample_order_items sample_schedule_items sample_unanswered_questions
python manage.py runserver            # http://127.0.0.1:8000

python manage.py makemigrations --check --dry-run   # verify no missing migrations
python manage.py test                         # all tests
python manage.py test product_app.test_api    # product/FAQ API tests
python manage.py check
python manage.py spectacular --validate --file /tmp/schema.yml
```

Before finishing a change, run `python manage.py check`, `makemigrations --check --dry-run`, `python manage.py test`, and the `spectacular --validate` command. All must pass.
