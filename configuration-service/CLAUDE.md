# CLAUDE.md: configuration-service

Guidance for Claude Code when working in `configuration-service/`.

## What this is

A Django REST API backend for Ansera Business Admin. It is consumed by `../frontend-app` (the Vite dev server runs at `http://localhost:5173`).

## Stack (keep to these; don't swap libraries without asking)

- **Django 6.1** (Python 3.12+). Project package: `config/`. Settings are in `config/settings.py`.
- **Django REST Framework** for all API endpoints: serializers + `APIView`/viewsets. Don't write plain Django `JsonResponse` views.
- **drf-spectacular** for OpenAPI 3 / Swagger docs. `DEFAULT_SCHEMA_CLASS` is set in `REST_FRAMEWORK`. The docs are at `/api/docs/` (Swagger UI) and `/api/redoc/`, and the schema is at `/api/schema/`. Use `@extend_schema` where auto-generated docs are unclear.
- **django-filter** (`django_filters` in `INSTALLED_APPS`) for list filtering/sorting: a `FilterSet` per list (e.g. `chat_app/filters.py` `ChatSessionFilter`), set with `filter_backends = [DjangoFilterBackend]` + `filterset_class` on the view (not globally). drf-spectacular documents the parameters automatically. Use `StableOrderingFilter`-style ordering (append `-id`) so pages stay stable. Prefer `ChoiceFilter` over `BooleanFilter` (which ignores invalid values instead of returning 400).
- **Pagination for rich lists:** `config.pagination.DetailedPageNumberPagination` (`page`, `page_size` ≤ 100; response adds `total_pages`, `current_page`, `page_size`, `has_next`, `has_previous`). Set it per view with `pagination_class`; the global default is still DRF's `PageNumberPagination`.
- **django-cors-headers**. `CorsMiddleware` must stay the **first** entry in `MIDDLEWARE`, above `SecurityMiddleware`, so that responses generated by other middleware still get CORS headers. `CORS_URLS_REGEX` limits CORS to `/api/`. Allowed origins come from `DJANGO_CORS_ALLOWED_ORIGINS` (default: the Vite dev server). Never use `CORS_ALLOW_ALL_ORIGINS = True`.
- **SQLite** (`db.sqlite3`, git-ignored, disposable: reset with `rm db.sqlite3 && migrate && loaddata … && createsuperuser`) for now. A real database will be integrated later, so keep the code database-agnostic (no raw SQLite-specific SQL).

### Chat flow (`chat_app/flow.py`, `prompts.py`, `tools.py`)

The user asked for this design ("draft", to be refined): per customer message,
1. Find the block: `ChatConfiguration.get_block(chat_state_id)` (type-strict) or `start_block` if missing.
2. **Extract** with `llm.generate_structured(system_prompt, history, schema)`: Ollama `format=<JSON schema>`, `STRUCTURED_OPTIONS` (temperature 0); invalid JSON → `LLMError` (502). Schemas come from `prompts.extraction_schema(block)` (static `EXTRACTION_SCHEMAS`, except DETAILS_COLLECTION, built from the block's fields), task prompts from `_EXTRACTION_TASKS`: START `{wants_to_order}`, PRODUCT_SELECTION `{items: [{product_id, quantity|null}], done_choosing}`, DETAILS_COLLECTION one nullable key per field (`number` fields typed as numbers), CONFIRMATION `{decision: confirm|change|none}`.
3. **Check deterministically** with `flow.CHECKS[block_type](extracted, data, products) → CheckResult(complete, missing, issues, go_back)`, updating `chat_state_data` in place. Never trust the LLM's values: products must be the business's active ones (`tools.active_products`) with 1 ≤ quantity ≤ `quantity_available`; PRODUCT_SELECTION then waits for the customer to confirm the cart (the user asked: recap, "anything else?", only then details): it completes only if `done_choosing` is true **and** the cart (`_cart()`: (product_id, quantity) pairs) didn't change in that message, or `items_confirmed` is already set; a changed cart clears `items_confirmed`; details go through `flow.clean_detail_value()` by type (text `max_length`, number parse + bounds, `EmailValidator`, phone pattern + 6–15 digits); known details are kept when the LLM returns null; ints exclude bools. Complete → `next_block_id`, and the loop runs again there (bounded), so one message can pass several blocks. `change` at confirmation → back to the block after START (data kept, so complete blocks pass straight through). A CONFIRMATION reached in the same message is not extracted (the customer hasn't seen the summary). Last block complete → `completed: true`, chat stays at that block, later messages skip extraction. A lone START (no `next_block_id`) never completes.
4. `save_flow_state()` writes `chat_state_id` / `chat_state_data` (validated) and fills an empty `display_name` from `details.name`. Saved before the reply, so it's kept if only the reply fails.
5. **Reply** with `llm.generate_chat_reply(system_prompt, history, Toolbox(business))`: `prompts.build_reply_prompt()` (business info, step + goal, collected data with a Python-computed total, still-needed list, issues, catalog for START/PRODUCT_SELECTION, per-type `_REPLY_INSTRUCTIONS` / `_COMPLETED_INSTRUCTIONS`). Up to `MAX_TOOL_ROUNDS` of tool calls; `tools.Toolbox` holds **read-only, business-bound** tools, each `name → (description, JSON-schema parameters, function(arguments))`: `get_product_description(product)` (the user asked: one product's full description by name/id via `find_product_description()`; errors list matches or what's on sale), `list_products` (descriptions cut by `description_preview()` to `DESCRIPTION_PREVIEW_LENGTH`), `list_faqs`. Never give tools write access or a business-ID argument. The catalog in prompts also uses previews, and the reply prompt tells the model to use `get_product_description` / `list_faqs` and to **say it doesn't know instead of making things up** (the user asked).
- **Details collection fields** (the user asked for this): `block['fields']`, a list of `{key, label, type, description?, required?, max_length? (text), min_value?/max_value? (number)}`, types in `constants.DETAIL_FIELD_TYPES` (`text`, `number`, `email`, `phone`). Validated by `validators._detail_field_errors` (1–`DETAIL_FIELDS_MAX` fields, key pattern `^[a-z][a-z0-9_]*$` ≤40 and unique, label ≤100, type-specific optional keys only, `max_length` 1–2000, min ≤ max, description ≤300); the limits are mirrored in `frontend-app/src/features/workflow/details.ts`. Always read them with `validators.block_detail_fields(block)`, which falls back to `constants.DEFAULT_DETAIL_FIELDS` (name + email) when `fields` is missing (old configurations). `required` (bool, missing = true; read with `validators.is_required_detail()`; at least one per block): the block completes when every **required** field is valid; optional ones are stored if given and their problems never block. The reply prompt (the user asked, after a bug where the bot said "order confirmed" while stuck on an unusual required field "BOO") says: not confirmed yet, never say it is (also a rule on every step: only when "Done (order confirmed)"); keep asking for required details every reply; optional ones once; use labels exactly as written (quoted in `describe_detail_fields`), never paraphrase or guess unusual ones. Collected values live in `chat_state_data.details[key]`; labels for prompts come from `prompts.detail_labels(config_json)` (all details blocks). A field with key `name` (string) fills an empty `display_name`. Checks take `(extracted, data, products, block)`.
- **Send message blocks** (`SEND_MESSAGE_BLOCK`, the user asked: "send a message, then move on, no extra functionality"): `config_json` requires `message` on them (non-blank, ≤ `CHAT_MESSAGE_MAX_LENGTH`) and rejects it elsewhere (`OPTIONAL_BLOCK_FIELDS`). In `advance()` they're handled before `CHECKS`: no LLM; append `{block_id, message}` to `Turn.sent_messages`, add to `finished`, move to `next_block_id` (none → `completed`); a block already sent this turn stops the loop (type-strict ids). `handle_customer_message()` appends them as `business-automated` before the LLM reply (also into `history`; `build_reply_prompt(just_sent=...)` adds a "Just sent" section); if the turn ended on a Send message block, no LLM reply (`debug.reply_system_prompt == ''`, the response is that message). `Turn.confirmation` records `len(sent_messages)`, so a failed order drops the messages queued after the confirmation. `debug.sent_messages` lists them.
- **Orders:** when a CONFIRMATION_BLOCK's check passes, `advance()` records `Turn.confirmation = (block, chat_state_data)`; `commit_turn()` (replaces the old `save_flow_state`) then, in one transaction with the session row locked, calls `checkout_app.services.place_order()` and stores `chat_state_data.order_id`. On `OrderError` it undoes the confirmation (block and data restored, no `completed`, problems in `turn.issues`). Only once per chat (`order_id` already set → skipped). See the `checkout_app` row above.
- History: last `HISTORY_MAX_MESSAGES` (20) messages; customer → `user`, both business senders → `assistant`. No order model yet: a completed flow doesn't reserve stock (`quantity_on_hold`) or create anything else.
- **Debug info:** `handle_customer_message()` returns `TurnResult(reply, debug)`. `advance()` records `Turn.steps` (per block: id, type, extraction prompt, `extracted`, check result, `chat_state_data` after) and `stop_reason`; `Toolbox.calls` records tool calls. Only the sandbox message endpoint returns it (`SandboxMessageResponseSerializer`: the message fields + `debug`); the public customer endpoint returns the message only. Never store it.
- Tests: `tests/test_flow.py` (end-to-end through the sandbox endpoint, including `debug`; custom detail fields; the checks as `SimpleTestCase`s).

### APIs and access control

- **Endpoints:** `product_app` has CRUD `ModelViewSet`s for `/api/products/` and `/api/faqs/`, registered with a `DefaultRouter` in `product_app/urls.py` and mounted at `/api/` in `config/urls.py`. `auth_app` has the auth endpoints under `/api/auth/` (`auth_app/urls.py`): `token/` (login), `token/refresh/`, `token/verify/`, `logout/` (blacklists the refresh token), and `me/` (`MeSerializer`: profile + `business` ID + `business_name`, read-only). The token views are thin subclasses of SimpleJWT's views (`LoginView`, `RefreshView`, `VerifyView`, `LogoutView`) that add Swagger docs under the `Auth` tag. `product_app` also has read-only `BusinessProductListView` / `BusinessFAQListView` at `/api/businesses/<int:business_id>/products/` and `/faqs/` (URL names `product_app:business-product-list` / `business-faq-list`). They list **all** of that business's records, including inactive products, and are paginated. There are no business-configuration or user-management APIs yet.
- **Business scoping (`auth_app/business_scope.py`):** reuse this for every business-owned model.
  - `IsBusinessMember`: object-level `obj.business_id == user.business_id`, so another business's record returns **403, not 404** (the user asked for 403). Users with no business get 403 on every unsafe method.
  - `BusinessScopedViewSetMixin`: the `list` action is filtered to the user's business; detail routes use the unfiltered queryset so the permission can return 403.
  - `BusinessFromUrlMixin`: for views with a `business_id` URL kwarg. It runs in `initial()`, after auth, so **401 comes first**. Then:
    - An unknown ID raises `ValidationError` → **400**. The user explicitly asked for 400 rather than 404.
    - Another business, or a user with no business, gets **403**.
    - Otherwise it sets `self.business`.

    Its `get_queryset()` must return `.none()` when `swagger_fake_view` is set (schema generation).
  - `BusinessOwnedSerializerMixin`: a `business` field that defaults to the user's business (`CurrentUserBusinessDefault`). Any other business raises `PermissionDenied` (403) in `validate_business`. Because it has a default, DRF's `UniqueTogetherValidator` still works for the per-business unique constraints.
- **`Product.quantity_sold` is read-only in the API.** `ProductSerializer.to_internal_value` explicitly returns 400 when it's sent, reported together with other field errors, instead of DRF's default of silently ignoring it.
- **DRF defaults (`REST_FRAMEWORK`):**
  - `DEFAULT_PERMISSION_CLASSES = IsAuthenticated`, so endpoints are private by default. Public endpoints must opt out: `RandomNumberView` sets `permission_classes = [AllowAny]` and `authentication_classes = []`.
  - `PageNumberPagination`, `PAGE_SIZE = 20`. List responses are `{count, next, previous, results}`.
  - Authentication, in order:
    1. **`JWTAuthentication`** (SimpleJWT, `Authorization: Bearer`). This is what `frontend-app` uses. Being first means unauthenticated requests get 401 with `WWW-Authenticate: Bearer`.
    2. `BasicAuthentication`, **only when `DEBUG`**, for Swagger's Authorize dialog.
    3. `SessionAuthentication`. drf-spectacular's Swagger UI sends the CSRF token, so it works there too.
  - **`SIMPLE_JWT`:** access 15 minutes, refresh 7 days, `ROTATE_REFRESH_TOKENS` + `BLACKLIST_AFTER_ROTATION` (needs the `rest_framework_simplejwt.token_blacklist` app, which is installed and migrated), `UPDATE_LAST_LOGIN`.
  - drf-spectacular's built-in SimpleJWT extension adds the `jwtAuth` security scheme to Swagger.
  - The frontend stores tokens in localStorage and refreshes them on 401 (see `../frontend-app/CLAUDE.md`).
- **Swagger docs:** keep the `@extend_schema_view` docs (tags `Products` / `FAQs`, summaries, 403 responses) up to date for new actions. Decimal fields are strings in the schema, so document numeric limits in `help_text`.

### Model conventions

- **Length limits are module-level constants** in each `models.py` (e.g. `PRODUCT_NAME_MAX_LENGTH`), reused in tests. Current limits:
  - Names: 150 characters.
  - Locations: 255 characters.
  - FAQ questions: 300 characters.
  - Descriptions: 2,000 (business) and 5,000 (product) characters.
  - FAQ answers: 10,000 characters.
- **`TextField(max_length=...)` isn't enforced by Django at the model level.** Always add `validators=[MaxLengthValidator(N)]` alongside it, as the existing models do.
- **Validation lives in both Django and the database.**
  - Field validators (`MinValueValidator`, `PositiveIntegerField`) catch bad values in forms, admin and serializers.
  - `Meta.constraints` catch them at the database level: `CheckConstraint` for non-negative prices and non-empty strings, `UniqueConstraint` for product name and FAQ question per business.
  - Django 6 uses `CheckConstraint(condition=...)`; the old `check=` argument was removed.
- **Quantity cap:** quantities are capped at `QUANTITY_MAX = 1_000_000` with a `MaxValueValidator`.
- **Primary keys:** `BigAutoField` (Django 6 default).
- **Admin:** register every model with `list_display`, `search_fields`, `list_filter` and `list_select_related`. Use `autocomplete_fields` for the `business` FK, which works because `BusinessConfigurationAdmin` has `search_fields`.
- **Serializers:** when you add them, reuse the model validators. DRF `ModelSerializer` picks them up automatically, and `UniqueConstraint` becomes a `UniqueTogetherValidator`.

### General

- All API routes live under `/api/`.
- Settings read from environment variables (`DJANGO_DEBUG`, `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`, `DJANGO_CORS_ALLOWED_ORIGINS`) with local-dev defaults. When adding a new setting, add it to `.env.example` and the README table.
- Add new dependencies to `requirements.txt` with a version range.
- After changing models, run `makemigrations` and commit the migration files. Don't edit applied migrations; the database is still disposable, but teammates may have it.

- **Test layout:** each app's tests are `tests.py` / `test_api.py`, except `chat_app` and `checkout_app`, which have a `tests/` package (`chat_app`: `test_models.py`, `test_api.py`, `test_flow.py`; `checkout_app`: `test_models.py`, `test_services.py`, `test_api.py`; the user asked, to keep app folders tidy). Run one with e.g. `python manage.py test chat_app.tests.test_flow`.

## Commands (run from `configuration-service/`, with `.venv` active or via `.venv/bin/python`)

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py loaddata sample_business_configurations sample_business_users sample_products sample_faqs sample_chat_configurations sample_chat_sessions sample_order_items
python manage.py runserver            # http://127.0.0.1:8000
python manage.py makemigrations
python manage.py makemigrations --check --dry-run   # verify no missing migrations
python manage.py test                         # all tests
python manage.py test product_app.test_api    # product/FAQ API tests
python manage.py check
python manage.py spectacular --validate --file /tmp/schema.yml
```

Before finishing a change, run `python manage.py check`, `makemigrations --check --dry-run`, `python manage.py test`, and the `spectacular --validate` command. All must pass.

## Environment notes for Claude

- The sandbox blocks listening on ports, so `runserver` can't be tested from inside Claude. Use Django's test client instead, and pass `HTTP_HOST='localhost'`, because `testserver` isn't in `ALLOWED_HOSTS` outside `manage.py test`.
- The user's shell sets `PYTHONPATH` to a Spark install, so `pip freeze` shows `pyspark`. Don't add it to `requirements.txt`.
